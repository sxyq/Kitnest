## 0. 结论速览

| 维度 | 参照对象 | FrsetNext 现状 | 判定 |
|---|---|---|---|
| iPhone 互传 | omdrop-owl | **已接入**：系统级隔空投送收发（v103，`TransferCastEngines.swift`） | ✅ 无协议级差距，Mac 原生路线优于 Linux 方案 |

## 1. 三个参照对象的定位

### 1.1 omdrop-owl（图二）——「iPhone 零安装互传」的价值证明

- **本质**：Linux 上的 AirDrop 无线电后端（OWL 用户态 AWDL 栈 + OpenDrop 收发），解决「AWDL 与路由器共用信道、Wi-Fi 不断线」的工程整合难题。
- **对我们的关键事实**：
  - **Linux 专用**（用户态注入无线帧，依赖 mac80211 驱动 profile，仅 MT7925 实测）；**macOS 不走这条路——Mac 本身就有原生 AWDL/AirDrop**；
  - 仓库未声明 license，代码不可复用，只能吸收思路；
  - 速度：收 ~1.3MB/s、发 ~490kB/s（作者自测）——**远低于 Mac 原生空投**；
  - iPhone 侧零安装是其核心价值。
- **结论**：该项目对 FrsetNext 的意义是**验证了「对端零安装」是传输功能的第一性原则**；实现上我们直接调用 macOS 原生能力即可，不做任何协议工作。

### 1.2 AndroMeld（图三）——Android↔Mac 融合的功能全景（商业闭源，¥88 买断）

技术底座：ADB（USB/无线）+ 视频流镜像（= scrcpy 同路线）+ 通知监听桥 + Finder 集成。其 14 项功能：

| # | 功能 | 实现层 |
|---|---|---|
| 1 | 屏幕镜像（低延迟音视频） | scrcpy 引擎 |
| 2 | **Meld Mode**（每个 App 独立 Mac 原生窗口） | 虚拟显示 + 窗口合成（招牌差异点） |
| 3 | Finder 集成（Android 存储进侧栏） | ADB 文件协议 + Finder 扩展 |
| 4 | 通知同步（手机→Mac 通知中心，可复制验证码） | NotificationListener + ADB 转发 |
| 5 | 双向剪贴板（文本+图片，适配微信） | ADB 剪贴板通道 |
| 6 | 电话（Mac 接听/拨打/静音） | 通话状态桥 |
| 7 | Mac 输入法打字到手机 | 输入事件转发 |
| 8 | 手机摄像头当 Mac 摄像头（Zoom/FaceTime） | 虚拟摄像头设备 |
| 9 | 触控板手势（Android 手势映射） | 事件转换 |
| 10 | 手机部件上 Mac 桌面 | App Widget 桥 |
| 11 | 存储用量视图 | ADB 文件统计 |
| 12 | APK 安装（APK/APKS/APKM/XAPK + 权限预检） | ADB install |
| 13 | MCP 服务器（AI 控制手机） | MCP over ADB |
| 14 | 远程连接（FCM 唤醒 + WebRTC P2P） | 远程通道 |

连接方式：USB / Wi-Fi（mDNS 发现）/ BLE 热点 / 远程 WebRTC。

### 1.3 Snow Shot（GitHub: hnztlyh/snow-shot-）——开源截图工具

Tauri（Rust + 前端）架构，990 commits 活跃维护，双许可证（商用/非商用）。六大特性：插件系统（录屏/OCR/翻译/AI 对话按需装载）、丰富标注（矩形/圆/箭头/文字/马赛克）、智能窗口识别（元素边界、全屏/窗口/滚动/焦点窗）、自定义快捷键、多种保存方式（本地/剪贴板/钉图）、自动更新 + 离线构建。

## 2. 逐项对标与接入情况

### 2.1 空投互传（omdrop-owl 路线）——已接入 ✅

**FrsetNext 现状**（`TransferCastEngines.swift` + `TransferDockView.swift`，v103/v105）：

| 能力 | 实现 | 状态 |
|---|---|---|
| 发送到 iPhone | `AirDropSendEngine.send(urls:)` → `NSSharingService(.sendViaAirDrop)` 系统面板 | ✅ |
| 从 iPhone 接收 | `AirDropReceiveWatcher` 监听 `~/Downloads`（DispatchSource，跳过 `.download`）→ 自动进「本地暂存」+ Toast | ✅ |
| iPhone 侧 | 零安装（系统原生） | ✅ |
| UI | 「传输与投屏」页 → 隔空投送区（发送按钮/可用性探测/引导文案） | ✅ |

**与 omdrop-owl 的等效性判定**：其核心价值（iPhone 零安装、双向互传）我们以**更低成本、更高速度**达成（原生 AWDL vs 用户态协议栈）。无差距。

**剩余增强点**（非协议，是「融合度」）：

| 增强 | 说明 | 优先级 |
|---|---|---|
| 剪贴板条目一键空投 | 剪贴板历史选中项 → AirDropSendEngine（当前仅「本地暂存」文件可发） | P1 |
| 截图/OCR 结果直接空投 | Capture 模块经 CaptureEventBus 接线到发送引擎 | P1 |
| 接收落点自定义 | 当前固定 ~/Downloads；可引导用户改系统设置或提供软链接方案 | P3 |
| 旧「扫码直传」UI 下线 | `LanTransferServer`（858 行）仍在 UI 中，方案文档计划「实测通过后删除」——建议明确保留还是下线（它对 Android/Windows 仍有零安装价值，见 §2.2 注） | P2 |

> **注**：扫码直传（qrcp 式 HTTP）与空投是互补而非替代——空投只通苹果设备，扫码直传通一切有浏览器的设备（含 Android/Windows）。AndroMeld 的 Finder 集成未落地前，建议**保留但降级为「通用互传」**，与空投并列而非对立。

### 2.2 Android 融合（AndroMeld 路线）——部分接入 ⚠️

**FrsetNext 现状**（v103 引擎层）：

| AndroMeld 功能 | FrsetNext | 说明 |
|---|---|---|
| ① 屏幕镜像 | ✅ 已接入 | `ScreenCastEngine.startMirror()` 拉起 scrcpy 独立进程（分辨率/码率可配、stay-awake） |
| ADB 设备发现 | ✅ 已接入 | `connectedDevices()`（后台执行，防主线程卡死） |
| ADB 路径探测 | ✅ 已接入 | brew/PATH/Android SDK 三路探测，无则引导安装 |
| ⑤ 双向剪贴板 | 🟡 半接入 | scrcpy 默认开启 clipboard autosync（**未显式传参，依赖默认值**）——建议显式 `--clipboard-autosync` 并在 UI 明示 |
| 无线连接 | 🟡 半接入 | `adb devices` 能看到已配对设备，但**无 `adb pair`/`adb connect` 配对流程 UI**（AndroMeld 有 mDNS 自动发现） |
| ② Meld Mode | ❌ | 虚拟显示 + 每 App 独立窗口——工程量大（需 `adb shell` 虚拟屏 + 窗口合成），见路线图 |
| ③ Finder 集成 | ❌ | Android 存储进 Finder 侧栏（需 Finder Sync 扩展或挂载方案） |
| ④ 通知同步 | ❌ | 需手机侧 NotificationListener（**唯一需要手机装 App 的功能**）或 `adb shell dumpsys notification` 轮询（有损） |
| ⑥ 电话 | ❌ | 通话状态/控制桥 |
| ⑦ 输入法 | ❌ | 事件转发（scrcpy 本身已支持 Mac 键盘打字到手机——**实际已随镜像获得**） |
| ⑧ 摄像头 | ❌ | 虚拟摄像头设备（系统插件） |
| ⑨ 手势 | 🟡 | scrcpy 镜像窗内支持基础触摸；触控板手势映射需自研 |
| ⑩ 部件 | ❌ | App Widget 桥 |
| ⑪ 存储视图 | ❌ | `adb shell df/storage_stats` 即可做，轻量 |
| ⑫ APK 安装 | ❌ | `adb install-multiple` + 权限预检（`aapt`/`apkanalyzer`） |
| ⑬ MCP | ❌ | 与 FrsetNext 的 AI 体系天然契合（我们的 AI 模块可作 MCP client 侧） |
| ⑭ 远程 | ❌ | FCM+WebRTC，重度且依赖外部服务，不建议近期做 |

**覆盖度**：14 项中 4 项已接入、3 项半接入、7 项未接入（其中输入法实际已由 scrcpy 附带获得）。

**落地成本与优先级**（按「投入产出比」排序，非 AndroMeld 功能顺序）：

| 优先级 | 项 | 成本 | 价值 |
|---|---|---|---|
| **P0** | 无线配对 UI（`adb pair` + `adb connect` + mDNS 发现） | 低（1-2 天） | 无线是日常主路径，当前缺入口 |
| **P0** | 剪贴板显式化（传 `--clipboard-autosync`，UI 明示） | 极低 | 半接入转正 |
| **P1** | 文件互推（`adb push/pull` 桥：暂存区 ↔ 手机） | 中（3-5 天） | 高频刚需，替代扫码直传的 Android 侧 |
| **P1** | 窗口镜像托管（scrcpy 窗口嵌入 FrsetNext 面板而非裸进程） | 中 | 体验统一（当前是「拉起一个陌生窗口」） |
| **P2** | 存储视图 + APK 安装 | 中 | 工具箱场景补全 |
| **P2** | 通知同步（`dumpsys notification` 轮询方案先行） | 中高 | 验证码场景是 AndroMeld 口碑功能 |
| **P3** | Meld Mode | 高（2 周+） | 招牌差异点，需虚拟显示 + 合成，风险最高 |
| **P3** | MCP 服务器 | 中 | 与自家 AI 体系联动时有独特价值 |
| **不做** | 远程连接 / 电话 / 摄像头 / 部件 | 高 | 依赖外部服务或系统插件，与工具栏定位不符 |

| 快捷键 | ✅ 自定义 | ✅ ShortcutManager（默认绑定 + 自定义） | ✅ 持平 |
| **窗口截图 / 窗口识别** | ✅ 元素边界自动识别 + 焦点窗 | 🟡 **原版本有 `.window` 模式**（docs/10-规格/06 反汇编 + docs/10-规格/20），重建版曾丢失；v113 已补回并对齐窗口选择器（悬停识别 + 单击截取） | ⚠️ **更正**：这不是「对标缺口」，是重建版丢失的原版能力（见彻查报告） |
| **元素级吸附** | ✅ 元素边界自动识别 | ❌ 区域框选为纯手动（原版区域模式亦无吸附证据） | ❌ 真缺口（仅元素级，窗口级已由窗口模式覆盖） |
| **插件系统** | ✅ 核心轻量 + 插件装载（录屏/OCR/翻译/AI） | 🟡 内部有模块注册表（`Registry.swift`：面板区段/设置页/状态项），但**非用户级插件**（不能动态装载第三方功能） | 🟡 架构取向不同，见下 |
| **自动更新** | ✅（Sparkle 类） | ❌（AppUpdateManager 在原版存在但未重建；且原版更新链已被补丁 C 禁用） | ❌ **缺口 2** |
| 离线构建 | ✅ | 🟡（工程可离线构建，但无分发打包策略文档化） | — |

**三个缺口的处置建议**：

1. **智能窗口识别（缺口 1，最影响体验）**：
   - 元素边界：`AXUIElementCopyElementAtPosition` + 遍历子元素取 frame，框选时鼠标悬停自动吸附到元素/窗口边缘（高亮描边）；
   - 焦点窗模式：`CGWindowListCopyWindowInfo` 取 frontmost window → 一键捕获（补 `CaptureMode.window`）；
   - 成本：中（3-5 天），需辅助功能权限（App 已有该权限的使用先例：全局事件监听）。
2. **插件系统（非缺口，是取向）**：Snow Shot 的插件化是为「跨平台 + 社区生态」；FrsetNext 的单体 Swift 工程 + 内部 Registry 已满足「功能模块化」。**不建议**做用户级插件沙箱（安全/签名/维护成本远超收益）；但可把「AI 对话/翻译」等按 Registry 规范持续模块化即可。
3. **自动更新（缺口 2，分发必需）**：DMG 分发后用户无法感知新版本。方案：Sparkle 2（ed25519 签名，AppKit 原生集成，1-2 天）或自建 GitHub Releases 检查。**建议 P1**——这与 §2.2 的 P0 项并列成为下一阶段两大主线。

## 5. 待用户决策

1. **扫码直传去留**：方案文档写「实测后删除」，但它对 Android/Windows 零安装互传仍有独特价值（空投不通它们、ADB 不通 iPhone）。建议：**保留并更名「通用互传」，与空投并列**——需确认。
2. **录屏入口**：当前录屏从 STATS 合并条/设置页进入（`StatsBarEngine` 记录 + Toast 引导），截图面板的 `CaptureMode` 无录屏项——是否把「录屏」提为截图面板一级入口？
3. **通知同步要不要手机 App**：AndroMeld 走手机辅助 App（闭源）；纯 ADB 方案（dumpsys 轮询）有损但零安装。按「对端零安装」第一性原则，建议只做 ADB 方案——需确认。
4. **Meld Mode 是否立项**：这是 AndroMeld 的招牌差异（App 级原生窗口），工程量 2 周+ 且风险高（虚拟显示兼容性因 ROM 而异）。建议先做第三批其他项，Meld Mode 单独评估。
