# 传输通道：两条逻辑的梳理 + 安卓互传协议的开源可行性

生成时间：2026-10-25（v119）
触发问题：用户提出「一个文件传输、一个隔空投送，太多了、意义不明」「原版是不是支持安卓？它是怎么支持的？」
「小米互传 / OPPO 互传有没有开源实现可以接进来」

---

## 一、先纠正一个前提：原版 Frset.app **没有任何传输功能**

这不是推测，是二进制实证。

| 探测项 | 结果 |
|---|---|
| 中文 UI 文案：传输 / 中转 / 发送 / 接收 / 互传 / 局域网 / 扫码 / 分享 / 设备 / 蓝牙 / 投送 | **全部 0 处** |
| `AirDrop` / `NearbyShare` / `QuickShare` / `MultipeerConnectivity` / `CoreBluetooth` / `NWBrowser` / `NetService` | **全部 0 处** |
| `NSSharingServicePicker` 2 处 | 是 `NSTextView` 的系统方法签名（框架反射表），不是业务调用 |
| `qrcode` 11 处 | 上下文是 `tool_qrcode`，与 `tool_uuid` / `tool_json` / `tool_translate` 并列 —— **工具箱的二维码生成器** |
| `upload` 10 处 | 上下文是 `uploadSample` / `uploadHistory` —— **性能监测的上传速率采样** |
| `bridge` 67 处 / `python` 1 处 | Sentry 崩溃上报 SDK 的属性名 / 一段语法高亮正则，与 Python 桥无关 |

**结论**：原版是纯 Mac 工具（剪贴板 / 截图 / 性能监测 / 工具箱），没有 AirDrop、没有扫码互传、没有云端中转、没有安卓支持。

所以「原版支持安卓」这个前提不成立。实际情况是：

| 功能 | 来源 |
|---|---|
| 文件中转（OPPO 中转站） | 从你自己的独立项目 `~/Desktop/Project/temp/OPPO 中转站/` 接进来的（Python 桥 + cookie） |
| 隔空投送 | 重建版 v103 自研（对标 omdrop-owl），调系统 `NSSharingService` |
| ADB 文件互传 | 重建版 v112 自研（对标 AndroMeld） |
| 通用互传（扫码） | 重建版自研（`LanTransferServer`，HTTP + 二维码） |

也就是说：**这四条通道全是重建版自己加的，不存在"原版是怎么做的"可参考**。

## 二、两条逻辑的本质（这才是"意义不明"的病根）

用户看到的三个区块，其实是**三种不同的传输范式**，但 UI 上按"协议"平铺，所以看不出该点哪个。

| 维度 | 文件中转（云端） | 隔空投送 | ADB 文件互传 | 浏览器扫码 |
|---|---|---|---|---|
| **方向** | 异步：先存，之后再取 | 同步：发完即达 | 同步 | 同步 |
| **网络** | 不需要同一网络 | 必须同一 Wi-Fi + 蓝牙范围 | USB 线或同一 Wi-Fi | 必须同一 Wi-Fi |
| **依赖** | OPPO 账号 + Python 桥 + 云端配额 | 系统 AWDL（苹果私有） | 开发者选项（USB 调试） | 浏览器（零安装） |
| **对方设备** | 任意（手机浏览器 / Mac） | 只有苹果设备 | 只有安卓 | 任何有浏览器的设备 |
| **容量上限** | 受云端配额限制 | 本机磁盘直传，无上限 | 手机存储，无上限 | 本机磁盘 |
| **速度** | 受宽带上传带宽 | Wi-Fi 直连（快） | USB 3.0 可达 100MB/s+ | Wi-Fi 直连 |
| **断点续传** | 天然支持（文件在云上） | 中断要重发 | 可重推 | 可重下 |
| **典型场景** | 出差 / 两台设备不在同一网络 / 隔天再取 | 同一房间，给同事的 iPhone 传个文件 | 手机与 Mac 之间大批量倒文件 | 给 Windows / 陌生设备传 |

**核心区别一句话**：
- **隔空投送 / ADB / 扫码 = 近场同步传输**（人在旁边，马上要）
- **文件中转（云端）= 异步跨网络中继**（人不在旁边，或者不是同一时刻）

两者是**互补**，不是重复。但 UI 上不该让用户自己判断"我该用哪个协议"。

## 三、安卓互传协议：开源实现调研

### 3.1 协议全景

| 协议 | 谁在用 | 开源实现（桌面端） | 手机端要求 | 国行小米/OPPO 能用吗 | 成熟度 | 许可 |
|---|---|---|---|---|---|---|
| **AirDrop**（AWDL） | 苹果 | OpenDrop / OWL（Linux 用户态 AWDL） | 苹果设备 | ❌ 安卓永远不可能（AWDL 是苹果私有物理层） | 已接入 | 无声明 |
| **Quick Share**（原 Nearby Share） | Google / 三星 / 海外机 | **NearDrop**（Swift，5.8k★）、RQuickShare（Rust） | **GMS 内置**（Android 6+） | ❌ **国行机没有 Google 服务，压根没有这个入口** | 成熟（v2.2.2，2026-09） | Unlicense（完全自由） |
| **互传联盟 MTA**（小米/OPPO/vivo/荣耀/一加/realme/魅族/中兴…） | 国产机全部 | **mtapy**（Python，唯一桌面实现） | **系统内置，零安装** | ✅ **全部有** | ⚠️ **demo 状态，只做接收，发送是 ToDo** | GPL-3.0 |
| 小米互联服务 | 小米官方 | ❌ 闭源（官方 macOS App） | 需装小米官方 App + 登录账号 | 仅小米 | 官方稳定 | 闭源 |
| LocalSend | 开源社区 | ✅ 完整（Flutter） | 需装 LocalSend App | ✅ 但要装 App | 成熟 | MIT |
| 小米手机「远程管理」 | MIUI 文件管理器 | FTP 客户端（Finder 自带） | 零安装，手动开 | ✅ 小米 | 稳定 | - |
| SMB | 通用 | macOS 自带 | 文件管理器「网络邻居」 | ✅ 小米/华为/OPPO 文件管理器都支持 | 稳定 | - |

### 3.2 互传联盟（MTA）协议本身的链路

```
手机（发送端）                          Mac（接收端）
   │  ① BLE 广播 service 00003331-...      │
   │◄──────────────────────────────────────│  BLE 扫描发现
   │  ② BLE 读 CHAR_STATUS → DeviceInfo    │
   │  ③ BLE 写 CHAR_P2P ← SSID/PSK/port    │  接收端把 P2P 凭据给手机
   │  ④ 手机开 WiFi P2P 热点 DIRECT-xxx    │
   │◄──────────────────────────────────────│  接收端加入该热点
   │  ⑤ WSS /websocket 版本协商             │
   │  ⑥ action:1 sendRequest（文件清单）    │
   │  ⑦ GET /download?taskId=X → ZIP 流     │
   │  ⑧ action:99 status ok                 │
```

关键点：**Mac 必须以 STA 身份加入手机开出来的 Wi-Fi Direct 热点**。macOS 没有 Wi-Fi Direct 协议栈。

### 3.3 为什么现在**不能**接 MTA（三个硬障碍）

| # | 障碍 | 具体后果 |
|---|---|---|
| 1 | **Wi-Fi Direct 在 macOS 不存在** | 只能用 `networksetup -setairportnetwork en0 "DIRECT-xxx" "密码"` 把 Wi-Fi 网卡**切过去** → **Mac 当场断网**（Wi-Fi 只能连一个网络），传完再切回来。还要 sudo 权限 + 临时 keychain 存密码。体验是"传个文件先断网 30 秒"。 |
| 2 | **mtapy 只做了接收方向** | 手机 → Mac 能收；Mac → 手机是作者 ToDo（README 明写 "send files to Android" 未完成），且整体标注 "not ready for production use"。等于接进来也只能收不能发。 |
| 3 | **GPL-3.0** | 不能静态链接进 Swift 二进制。只能像现在的 OPPO 桥那样，以**独立 Python 子进程**调用（法律边界比链接干净，但仍需随包分发源码）。而 OPPO 桥是自有脚本，没有这个负担。 |

补充：mtapy 作者在 macOS 上的实测路径也是"手机发起 → Mac 收到 → 手机弹窗让你连 DIRECT-xxx"。**你没法在 Mac 上主动发起**。

### 3.4 Quick Share（NearDrop）为什么也不行

NearDrop 代码质量很好（Swift、Unlicense、5.8k star、2026 年还在更新），但：

- 它实现的是 **Google Quick Share**，安卓侧入口在 **Google Play 服务**里；
- **国行小米/OPPO/vivo 出厂没有 GMS** → 手机分享面板里根本没有 "Quick Share" 这个选项；
- 你的 Xiaomi Pad 6S Pro（Android 16 国行）实测分享面板只有「小米互传」。

所以 NearDrop 对你的设备**零收益**。除非刷国际版 ROM。

## 四、那"更快"到底该怎么做

### 4.1 现状速度对比（同一台小米平板，实测环境）

| 通道 | 理论/实测 | 需要什么 |
|---|---|---|
| ADB（USB 3.0） | **100 MB/s+**（已是满速） | USB 线 + USB 调试（一次设置） |
| ADB（无线 5GHz） | 20-40 MB/s | 一键无线（已做） |
| 浏览器扫码（Wi-Fi） | 15-30 MB/s | 同一 Wi-Fi |
| 隔空投送 | 苹果设备间 30-80 MB/s | 只通苹果 |

**结论：ADB 已经是最快的安卓通道**，比任何互传协议都快（互传联盟走 WiFi P2P 也就 20-40MB/s）。用户觉得"慢"，很可能是因为走了无线的 ADB 或扫码 HTTP，而不是 USB。

### 4.2 真正值得做的三件事（按性价比）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| **P0** | **ADB 传输进度条 + 速度显示** | 现在只有一个 `adbFileStatus` 文本，大文件时用户以为卡死。加进度/速率，观感立刻不同 |
| **P1** | **USB 插入自动切有线通道** | 检测到 `usb:` 设备就用 USB（快 5 倍），没插才走无线 |
| **P2** | **SMB 反向共享**（Mac 开共享 → 手机文件管理器「网络邻居」） | 零安装、满速、可浏览目录、双向，且小米/华为/OPPO 文件管理器原生支持。比 MTA 现实得多 |
| P3 | Mac 开热点 / 手机开热点 作为"没有共同 Wi-Fi"时的兜底 | 消掉"必须同一 Wi-Fi"的前提 |
| ❌ 暂缓 | MTA（mtapy） | 断网 + 只收不发 + GPL，投入产出比不成立 |
| ❌ 不做 | Quick Share | 国行机无 GMS |

> 如果哪天 mtapy 补上发送方向、且 macOS 有了不用切网卡的做法（比如手机支持"热点 + 保持 5G 上行"），再评估。

## 五、UI 改造：从"按协议"改成"按动作"

### 5.1 改之前（用户原话：太多了、意义不明）

```
文件中转
├─ 隔空投送            ← 发文件
├─ 文件互传 · Android   ← 发文件
├─ 云端 · OPPO 中转     ← 发文件（但其实是异步）
└─ 本地暂存
```
三块都在"发文件"，用户不知道该点哪个。

### 5.2 改之后（v119）

```
文件中转                         ⚙
─────────────────────────────────
[ 发送 ]  [ 接收 ]  [ 云端 ]      ← 按动作分段
─────────────────────────────────
发送：已选 3 项，选一个出口发出去   [+ 添加文件]
┌────────┐ ┌────────┐ ┌────────┐
│ 隔空投送 │ │ 安卓 ADB │ │ 浏览器扫码│
│ 苹果设备 │ │ 线/无线  │ │ 任意设备 │
└────────┘ └────────┘ └────────┘
─────────────────────────────────
本地暂存  12 项          [全选][清空]
┌────┐ ┌────┐
│文件 │ │文件 │    ← 双列卡片（不变）
└────┘ └────┘
```

- **发送**：从暂存勾选 → 三个出口并列（苹果 / 安卓 / 浏览器），一眼看懂"按对方设备选"
- **接收**：隔空投送（自动入暂存，已监听）/ 从手机拉取（ADB）/ 浏览器上传（出码）
- **云端**：OPPO 中转（未启用时显示引导，不再整块消失）
- **本地暂存**：三条通道共用的池子，常驻底部

这样用户的心智变成：**文件先进池子，再从三个出口发出去**，而不是"我要用哪个协议"。

## 六、结论速览

1. **原版没有任何传输功能** —— "原版支持安卓"是误解；四条通道全是重建版自研/接入的。
2. **隔空投送 ≠ 文件中转**：一个是近场同步（苹果专用），一个是异步跨网（云端中继）。互补，但 UI 不该按协议平铺 → 已改成"发送 / 接收 / 云端"三段。
3. **安卓互传的开源现状**：
   - Quick Share（NearDrop）→ 国行机无 GMS，**用不了**；
   - 互传联盟（mtapy）→ 协议对了，但 **demo + 只收不发 + 会断网 + GPL**，**现在不能接**；
   - 小米互联服务 → 闭源官方 App，不是我们能集成的；
   - **ADB 已是最快的安卓通道**（USB 3.0 100MB/s+），比互传联盟还快。
4. **下一步该做的是**：给 ADB 加进度/速率、USB 优先、SMB 反向共享；而不是接一个会断网的 demo。

# 补充（v120，2026-10-25）：两个设备的最终形态 + 三个疑问的答案

## 七、「让安卓手机用苹果隔空投送」——技术上为什么做不到

用户提到「之前的项目不是可以让安卓用苹果的隔空投送吗」。这里需要分清：

| 项目 | 实际是什么 | 能跑在哪 |
|---|---|---|
| **omdrop-owl / OWL** | 用户态 AWDL 协议栈 + OpenDrop 收发，让**电脑**伪装成苹果设备收/发空投 | **Linux**（依赖 mac80211 驱动的 monitor mode + 原始无线帧注入，作者仅在 MT7925 网卡实测） |
| OpenDrop（seemoo-lab） | AirDrop 协议的 Python 实现 | Linux / macOS（收为主） |
| **不存在** | 安卓端的 AWDL 实现 | — |

**安卓要做同样的事，需要同时满足三个条件**：
1. **root**（要往无线网卡注入原始 802.11 帧）；
2. Wi-Fi 芯片驱动支持 **monitor mode / frame injection**（手机厂商固件通常直接关掉）；
3. 一套跑在 Android 上的用户态 AWDL 栈（现有实现都绑 Linux 的 `AF_PACKET`）。

**结论：没有可用的开源实现，普通用户不可能做到。** AirDrop 走的是苹果私有 AWDL 物理层，不是普通的 Wi-Fi/BLE 广播。

### 现实可行的等效方案：Mac 当桥

```
安卓手机 ──(扫码 / ADB)──► Mac 暂存 ──(隔空投送)──► iPhone
```

这条路我们**已经具备**：安卓把文件传到「本地暂存」→ 勾选它 → 点「苹果设备」→ 系统空投面板选 iPhone。
这就是「安卓 → iPhone」目前唯一零安装、稳定的路径；UI 上已在「接收」段加了说明。

## 八、快传联盟（MTA）的开源实现，到底有没有能用的

| 项目 | 语言 | 平台 | 发现 | 接收 | **发送** | 状态 | 能用在 macOS 吗 |
|---|---|---|---|---|---|---|---|
| **mtapy**（est/mtapy） | Python | macOS（作者实测） | ✅ BLE | ✅ | ❌ ToDo | demo，作者自述 "not ready for production" | ⚠️ 能跑，但只收不发 + 会断网 + GPL |
| **cattysend**（Tinnci） | Rust | **仅 Linux** | ✅ BlueZ | ✅ | 🚧 WIP | 活跃开发中 | ❌ 依赖 BlueZ + NetworkManager |
| CatShare（kmod-midori） | Kotlin | **Android App** | ✅ | ✅ | ✅ | 可用（需 Shizuku 拿 MAC） | ❌ 是手机端 App，不是桌面端 |

两个桌面实现都卡在同一处：**macOS/Linux 没有 Wi-Fi Direct**。
- Linux 用 NetworkManager 接管 P2P（cattysend 明说"连接性权衡"：并发 Wi-Fi 操作有困难）；
- macOS 只能用 `networksetup -setairportnetwork` 把网卡整个切到手机热点 → **断网**。

**所以截至 2026-10，没有"能在 macOS 上既不装驱动、又不断网、还能双向发"的 MTA 实现。**
等哪天有，我们再接；现在接等于让用户每传一次文件断网 30 秒，且只能收不能发。

## 九、不在同一局域网时，扫码还能不能传

**不能。** 扫码给的是 `http://<Mac 的局域网 IP>:8787/s/<token>`，跨网络不可达（除非做端口映射/公网中转）。

四个现实选项：

| 方案 | 要做什么 | 评价 |
|---|---|---|
| **手机连 Mac 热点**（或反过来） | 系统设置里开「互联网共享」/ 手机开热点 | 最省事，一次设置就一直同网 |
| **OPPO 云端中转** | Mac 端登录 OPPO 账号 | 适合"传给自己另一台设备"；对方不是账号主人时用不了 |
| **LocalSend**（手机装 App） | 手机装一次，之后全自动发现 | 94k star、Apache-2.0，跨网不行但局域网体验最好 |
| croc / WebRTC 中继 | 需要信令/中继服务器 | 要部署服务，本轮不做 |

UI 上已在二维码弹层写明前提：「手机与本机连同一个 Wi-Fi（扫码走局域网，不经服务器）」。

## 十、v120 的最终形态：两类设备

```
发送  已选 2 项，选对方是什么设备            [+ 添加文件]
┌────────────────────┐  ┌────────────────────┐
│      ◉ 波纹          │  │      ▣ 二维码        │
│     苹果设备          │  │     安卓 / 其他       │
│   隔空投送 · 零安装    │  │   扫码即传 · 零安装    │
└────────────────────┘  └────────────────────┘
大文件/批量走 ADB 更快（需开发者选项）  ADB 直传
```

- **只剩两类目标设备**，用户不需要懂协议；
- **ADB 降级**成一行小字链接（要开发者选项，日常太麻烦）；
- 扫码弹层区分「有选中文件」（定向下载）和「没选文件」（双向互传 + 对方可上传）。

## 十一、两个实测 bug 的根因（都是这次定位的）

| 现象 | 根因 | 修复 |
|---|---|---|
| **隔空投送点了没反应** | `airdrop` 这个 SF Symbol **在本机不存在**（`NSImage(systemSymbolName:)` 返回 nil）→ 图标空白，看起来像"没显示"；全项目 9 处都用了它 | 全部换成 `dot.radiowaves.left.and.right` |
| **点击十分卡顿，面板迟迟不出现** | ① 面板是 `FloatingPanel`（`.nonactivatingPanel`），点击不激活 app，而 `NSSharingService.perform` 在 app 未激活时**不显示系统面板**；② 首次实例化 `NSSharingService(named:.sendViaAirDrop)` 同步初始化 AWDL，阻塞主线程 1~3s | 实例缓存 5 分钟 + 页面 onAppear `warmUp()` 预热 + 先 `NSApp.activate` 再异步 `perform`（延迟 0.12s） |

顺带：全项目 SF Symbol 批量校验发现 **4 个无效符号**（`airdrop` / `app.badge.plus` / `person.crop.circle.badge.key` / `thermometer.slash`），已全部替换为真实存在的符号。
