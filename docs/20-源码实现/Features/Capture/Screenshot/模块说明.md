# Capture/Screenshot —— 截图热链路模块说明（feature_id: CAPTURE）

> 截图核心链路：原生像素抓屏、选区覆盖层、动作工具条、权限管理、取色器。对应源码：`apps/FrsetNext/Sources/Features/Capture/Screenshot/`（**20** 个 `.swift` / **6 556** 行，2026-11-23 实测）。
> 源笔记：`docs/90-历史归档/深度阅读/C1-capture.md` §3.35（ScreenshotManager）、§3.37（ScreenshotOverlay）等。本说明按当前源码核实更新。

## 模块职责

截图从快捷键到落盘的完整热链路：权限鉴权 → 多屏抓帧（原生像素）→ 覆盖层选区 → 裁剪/落盘/登记 → 动作分流（保存/复制/OCR/钉图/标注/翻译等 12 种）。附带取色器、延时截图、色值面板。

## 入口与主要调用链

### 多图长截图拼接（2026-11-27）

`CaptureSectionView.pickAndStitch` 选图并沿用原帧数条件，在原 `userInitiated` 闭包内连续调用 `Stitcher.stitch` 与 `ImageProcessor.pngData`；主线程再调用 `saveStitchedResult(_:pngData:overlaps:)`，依次执行原保存、最近列表、历史、图像事件和触感。编码失败仍走原提示；写盘仍在主线程，实际长图落盘及入口交互待测。两文件正式定向类型编译通过。

### 区域截图热链路（2026-11-24 v293 四阶段）

```
快捷键/按钮 → ScreenshotManager.handleScreenshotShortcut / captureRegion
  → startCapture(flow:)                         [@MainActor]
      ├─ captureGeneration += 1（旧轮次作废）
      ├─ hasPermission 已授权 → 跳过跨线程权限探测
      └─ 日志「快捷键→冻结开始 N ms」
  → beginCapture(flow:generation:)              [@MainActor]
      ├─ ① 冻结阶段：不建可见窗、不激活
      │    ScreenSnapshot.beginEpoch()
      │    streamScreenSnapshots(screens, priority: 光标屏, budget: CaptureBudget)
      │      ├─ 并发度 2（withTaskGroup，有界）
      │      ├─ captureScreenForScreenshot(epoch, toast, budget)
      │      │    └─ NativeRegionCapture.captureScreenOnDisplay(BMP → 必要时 PNG,
      │      │         limit = min(4s, 预算剩余))
      │      └─ 每块抓完 → makeOverlay() 建**不可见**覆盖层（接回调 + 预置窗口命中）
      ├─ ② 全部冻结完成 → 日志「截图冻结完成 N ms」
      └─ ③ showOverlays()：NSApp.activate **一次**
            光标屏 makeKeyAndOrderFront，其余 orderFront（不抢 key）
  → 用户拖拽/单击 → onCommit / onWindowCommit / onWindowsCommit / onDesktopCommit
  → commitRegion / commitWindow / commitWindows / commitFullScreen
      ├─ 取 overlayView.snapshot（触发时冻结帧）→ closeOverlays()（释放整屏图）
      ├─ ImageProcessor.crop（双轴倍率独立）
      ├─ PNG → stagePNG/savePNG → registerCaptured
      └─ CaptureActionChain.present / handle(action:)
```

**为什么不在第一块抓完就显示**（2026-11-24 C1/C2）：旧实现第一块抓完就
`NSApp.activate` + `makeKeyAndOrderFront`。非镜像双屏下，这次激活会让**还没抓的副屏**
上原本的悬停预览 / 菜单 / 浮层消失，副屏冻结到的是被 Kitnest 自己改过的画面；
而且哪块先完成不确定，副屏先完成时会把键盘焦点抢走。现在冻结与显示解耦，
宁可多等慢的那块（v292 实测双屏第二块 +66~70ms），也不破坏画面真实性。

**覆盖层显示的是冻结帧**：`ScreenshotOverlayView.snapshot` 直接进
`CALayer.contents`，压暗是静态层，十字准线是 `CAShapeLayer`，只有高亮/提示画在
`OverlayCanvas` 上并做局部失效——鼠标在空白处移动不再整屏重绘。

### NativeRegionCapture 通道选择依据

| 通道 | 尺寸 | 锐度 | 结论 |
|---|---|---|---|
| `screencapture -x`（整屏） | 3420×2224 | **12.38** | ✅ 唯一真 Retina |
| `screencapture -x -R…` | 同上 | 12.38 | 慢且不稳定（0.5–1.5s） |
| `screencapture -x -o -R…` | 同上 | 8.34 | ❌ `-o` 去阴影导致掉 1x |
| SCK `.best` | 同上 | 7.14 | ❌ 插值放大 |
| `CGDisplayCreateImage` | 同上 | 8.31 | ❌ 放大 |
| legacy `CGWindowListCreateImage` | 3466×2348 | 8.60 | ❌ 放大 |

**结论**：整屏 `screencapture` → 内存裁剪。约 208ms。绝不能加 `-o`。

### BMP 优先传输

BMP 204ms / PNG 389ms（空闲）；满载时 BMP 198ms / PNG 424ms（最慢 1487ms）。PNG 编码线程在高负载下被饿死，是"等好几秒"的根因。14.7MB BMP 写在页面缓存里，读回比解 PNG 快（42ms → 21ms）。

### 会话预算（v293）

旧实现每条通道各自 4s：BMP 超时 → PNG 再 4s → SCK 再 4s，最坏一次截图串行等 12s。
现在 `CaptureBudget` 给整轮一个 deadline（冻结阶段 2.4s，单通道上限 4s 且只拿剩余），
`NativeRegionCapture` 在剩余不足 300ms 时不再开 PNG 回退。具体数值见
`docs/40-修改记录/Capture/变更记录.md`；未做实测前不得写成「已验证更快」。

### 临时文件与内存（v293）

BMP 单张约 14.7MB。旧实现 `Data(contentsOf:)` 先整体复制再交给 ImageIO（多一次 14.7MB
memcpy + 一份峰值）；现在按 URL 建 `CGImageSource` 并 `shouldCacheImmediately` 立即解码，
临时文件在 `defer` 里删除。双屏两张 3420×2224 冻结帧各约 30MB，`closeOverlays()` 会显式
`snapshot = nil` 断引用，不等窗口释放。

### CaptureEpochCounter 代次取消

连按快捷键时上一轮 `screencapture` 进程必须能被叫停。旧实现只挡"旧图不铺覆盖层"，进程仍在跑、和新的抢 WindowServer——越按越慢。`beginEpoch()` 返回代次号，`isCurrentEpoch(_:)` 校验。

## 数据流与状态变化

```
isCapturing = true
  → captureGeneration += 1
  → streamScreenSnapshots（并发度 2）
      ├─ 每屏完成 → 增量铺覆盖层（overlays.append + orderFront）
      └─ 全部完成 → isCapturing = false（或失败时提前 false）
用户操作 → onCommit → closeOverlays()（orderOut + removeAll）
  → handle() → registerCaptured → recent 插队（≤60）→ 历史库
```

`ScreenshotManager` 内部状态：`recent: [CapturedImage]`（≤60）、`isCapturing`、`ocrText`、`isRecognizing`、`statusMessage`、`hasPermission`、`qrPayloads`；私有 `overlays`、`thumbCache`（NSCache 48 项/20MB）、`pendingFlow`、`lastSelectionAppKit`、`lastHistoryPath`、`captureGeneration`、`snapshotTask`。

## 异常和取消处理

| 场景 | 处理 |
|---|---|
| 权限假阴性 | `probePermission` 用 `SCShareableContent` 能否枚举 display 作权威判据 |
| TCC 反复弹窗 | `init` 刻意不做 SCK 探测（`SCShareableContent` 是授权 API，放 init 会每次启动请求权限） |
| 连按快捷键 | `CaptureEpochCounter` + `snapshotTask.cancel()` |
| `screencapture` 超时 | 4s 硬超时 → `task.terminate()` |
| 镜像屏 | 增量铺层时镜像屏退回归集后统一铺（防后铺的屏拍到先铺的覆盖层） |
| 延时取消 | Esc/Delete/右键（local monitor） |
| 取色挂起回调 | `pickColor` 先以 nil 结算旧 pending → `finish(nil)` → 再登记新 `pendingPick`（顺序不可变） |

## 已知限制 / 历史坑

1. **`sckCaptureSync` 禁止主线程调用**（信号量阻塞）。
2. **`crop` 双轴独立缩放**：`sx = image.width/screenFrame.width`、`sy = image.height/screenFrame.height`，不假设相等（v149 拉伸事故修复）。
3. **覆盖层窗口枚举在 `init` 只做一次**：打开覆盖层后新出现的窗口识别不到。
4. **`CaptureActionChain.tools` 是计算属性**：每次访问重建 12 个带闭包的 struct。
5. **`closeOverlays()` 只 `orderOut`**：`DeleteKeyMonitor` 要等视图 deinit 才释放。
6. **`Eyedropper` 恰好一次 resume 契约**：`pendingPick` 登记顺序错了会 continuation 悬挂或双重 resume。
7. **`DelayedCaptureController.currentScreen()` 强解包 `screens.first!`**：虚拟机/远程会话可能崩。
8. **文件名模板 `{seq}` 当日序号**：跨日自动重置。
9. **固定比例存"宽:高"两个整数**：不引入浮点避免比较抖动。
