# 互传联盟（MTA）接入 · 源码级深度调研

调研时间：2026-10-25
调研方式：Research Router（open-source / deep）→ GitHub 源码快照 → 逐文件阅读 → 本机实测
调研对象：`est/mtapy`（Python，唯一 macOS 实现）、`Tinnci/cattysend`（Rust/Linux）、`kmod-midori/CatShare`（Android）

---

## 一、结论先行：不是"不能接"，是"要付代价"

| 问题 | 答案 |
|---|---|
| 能不能在 macOS 上接入互传联盟？ | **能**。协议链路里 macOS 原生 API 全部具备 |
| 现在为什么没接？ | 因为「接收端要加入手机开的热点」→ 若 Mac 靠 Wi-Fi 上网，**传输期间会断网**；且 mtapy 只做了接收方向 |
| 断网有解吗？ | **有**：Mac 走**有线网络**（雷雳/USB-C 以太网）时，Wi-Fi 网卡可专用做 P2P，全程不断网 |
| 发送方向（Mac → 手机）呢？ | 协议状态机已存在（`sender.py`），缺 I/O；且需要 Mac 开软 AP |
| 值不值得接？ | 取决于你能不能接受「无 Wi-Fi 上网时短暂断网」。能接受就值得，体验最接近原生 |

## 二、协议全链路（源码实证）

```
手机（Sender）                              Mac（Receiver）
   │ ① BLE 广播 00003331-0000-1000-8000-008123456789   │
   │◄──────────────────────────────────────────────────│ CoreBluetooth 扫描
   │ ② Mac 连 BLE，读 CHAR_STATUS(00009954) → DeviceInfo │
   │ ③ Mac 写 CHAR_P2P(00009953) ← P2pInfo(SSID/PSK/port)│
   │ ④ 手机开热点 DIRECT-xxx                            │
   │◄──────────────────────────────────────────────────│ networksetup -setairportnetwork
   │ ⑤ WSS /websocket（自签证书，跳过校验）              │
   │ ⑥ action:0 versionNegotiation → ack               │
   │ ⑦ action:1 sendRequest（文件名/大小/数量）          │
   │ ⑧ 用户点「接受」→ action:99 status ok              │
   │ ⑨ GET /download?taskId=X → ZIP 流                  │
```

关键常量（`constants.py`）：
- 广播服务：`00003331-0000-1000-8000-008123456789`
- 主服务：`00009955-...`，状态特征 `00009954-...`，P2P 凭据特征 `00009953-...`
- 加密：**ECDH P-256 + AES-256-CTR**，IV 固定 `0102030405060708` —— 只加密 BLE 上交换的 SSID/PSK，文件走 HTTPS（自签证书，`CERT_NONE`）

**这个设计对我们非常有利**：发现和凭据交换走 BLE（macOS 完全支持），只有实际传输走热点。

## 三、macOS 到底缺什么

| 能力 | macOS | 说明 |
|---|---|---|
| BLE 中心设备（扫描） | ✅ CoreBluetooth | mtapy 用 pyobjc 验证通过 |
| BLE 外围设备（广播） | ✅ CoreBluetooth | `CBPeripheralManager` |
| ECDH P-256 | ✅ CryptoKit | `P256.KeyAgreement` |
| AES-256-CTR | ✅ CommonCrypto | `CCCrypt(kCCModeCTR)` |
| 加入指定 Wi-Fi | ✅ `networksetup -setairportnetwork` | **会切换网卡** |
| WSS 客户端（忽略证书） | ✅ `URLSessionWebSocketTask` + delegate | 需要自定义 `didReceive challenge` |
| HTTPS 下载 | ✅ `URLSession` | 同上 |
| **Wi-Fi Direct（P2P）** | ❌ | 没有公开 API，Apple 用私有的 AWDL 代替 |

**唯一缺的就是 Wi-Fi Direct。** 但 MTA 用 BLE 做发现，实际只需要「一个能连的 Wi-Fi 热点」，不要求走 Wi-Fi Direct 的协商协议。

## 四、断网问题的三种解法

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 有线 + 无线分工**（推荐） | Mac 用雷雳/USB-C 以太网或 Studio Display 上网，Wi-Fi 网卡专职做 P2P | 需要一根网线/网卡；传完切回原 Wi-Fi |
| **B. 接受短暂断网** | `networksetup` 切到手机热点 → 传完切回原 SSID | 传输期间断网（传 1GB 约 30 秒） |
| **C. 不用 MTA，走 HTTP** | 现成的「通用互传」：同 Wi-Fi + 浏览器 | 需要同一 Wi-Fi，但零代价 |

判断依据（运行时可以自动检测）：读 `networksetup -listnetworkserviceorder`，如果以太网排在 Wi-Fi 前面，说明主网络不是 Wi-Fi → 方案 A 可行，此时 MTA 可以放心接。

## 五、本机实测数据

### 5.1 mtapy 能否跑起来（macOS 26 / Apple Silicon）

```
$ PYTHONPATH=src python demo.py --auto-connect --timeout 12
MTAPY DEMO STARTING...
[RECV] 📡 Advertising as 'MacBook Pro' | Waiting for Android...
[SCAN] 🔍 Scanning for 10.0s...
```

**启动成功，BLE 广播与扫描均正常。** 依赖：`bleak` + `websockets` + `cryptography` + `pyobjc-framework-CoreBluetooth`。
（本项目已把它放在 `tools/mtapy/`，附带 GPL-3.0 LICENSE，以独立进程方式调用，不链接进二进制。）

### 5.2 现有通道的真实速度（小米平板 6S Pro，120MB 单文件）

| 通道 | 速率 | 备注 |
|---|---|---|
| ADB over USB | **38.2 MB/s** | 3.14 秒传完 |
| ADB over Wi-Fi（5GHz） | **21.2 MB/s** | 5.66 秒传完，同 Wi-Fi |
| 互传联盟（Wi-Fi P2P）| 理论 20-40 MB/s | 与无线 ADB 同量级 |

**结论：MTA 并不会比无线 ADB 更快**，它的价值在"手机上点分享就能发"，而不是速度。

### 5.3 adb push 的进度陷阱（实现时踩到的）

```
$ adb push -p big.bin /sdcard/...
/tmp/big.bin: 1 file pushed, 0 skipped. 38.2 MB/s (125829120 bytes in 3.140s)
```

**管道（非 tty）下 adb 不输出百分比**，只有最后一行汇总。所以进度改为「每 0.7 秒 `adb shell stat -c %s <远端路径>` 轮询」，
用已传字节 / 总字节算百分比，整体平均算速率与剩余时间。

## 六、Swift 重写的可行性（不用 Python）

| 层 | macOS 原生实现 | 工作量 |
|---|---|---|
| BLE 扫描 + 读/写特征 | CoreBluetooth（`CBCentralManager` + `CBPeripheral`） | 中 |
| P2P 凭据解密 | CryptoKit（P-256）+ CommonCrypto（AES-CTR） | 中 |
| 加入热点 | `Process` + `networksetup`，传完切回 | 低 |
| WSS 协商 | `URLSessionWebSocketTask` + 忽略证书 | 中 |
| ZIP 下载解压 | `URLSession` + 已有 7zz | 低 |

**全部有原生 API，不需要 Python 运行时。** 预计 1-2 天可做出「手机 → Mac」的接收端。

## 八、下一步（需拍板）

1. **先验证**：双击 `tools/mta-listen.command`，手机上「分享 → 小米互传 → 选 Mac」，看能否收到文件。
   - 能收到 → 协议通，进入第 2 步
   - 收不到 → 看日志（BLE 是否发现、是否卡在连热点），再定位
2. **决定接入形态**：
   - **快**：Python 子进程（现成，但依赖 50MB venv、GPL 需随包分发源码）
   - **干净**：Swift 重写（1-2 天，无外部依赖，可打包进 app）
3. **决定断网策略**：优先检测有线网络；没有有线时给用户一个明确开关（"传输时允许短暂断网"）。
