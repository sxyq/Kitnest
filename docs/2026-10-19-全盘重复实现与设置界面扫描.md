## A. 重复实现（按严重度排序）

### A1. 数据采集层双轨（最严重，性能+维护双重成本）

| | C 引擎（活跃） | Swift（大部分白采） |
|---|---|---|
| 入口 | `frset_stats_tick.m:107 statsTick()`，NSTimer 0.5s | `MonitorSampler.sampleOnce()`（MonitorSampler.swift:175），用户间隔 0.5–10s |
| CPU | `frset_cpu_sample` | `MonitorReader.readCPU()`（host_processor_info） |
| 内存 | `frset_mem_sample` | `readMemory()`（host_statistics64 + sysctl swap） |
| 网络 | `frset_net_sample` | `readNetworkRate()`（getifaddrs） |
| 磁盘 | `frset_disk_sample` | `readDiskRate()`（IOBlockStorageDriver 逐盘读属性） |
| 电池 | `frset_battery_sample`（1s 一次） | `readBatteryLevel()` + `readPower()`（IORegistry） |
| 温度 | `frset_smc_scan` 600 键（后台线程，v49 优化） | `readTemperatures()` 6 键，**每次采样开/关一次 SMC 连接，带 150ms 信号量等待** |
| 负载 | `frset_loadavg` | `reader.loadAverages()` |

**闭环证据**：`MonitorSampler.swift:177` 先调 `StatsDataProvider.shared.refresh()`（C 数据），`:179` 再跑 `reader.readResult()`（Swift 全量），随后 **:188-212 把 CPU/系统/用户/空闲/每核、内存 used/total、磁盘读写、网络上/下行、电池电量全部覆盖为 `g_snap`**（v76「全盘统一数据源」修复）。即 Swift 侧 17 个字段里约 12 个当场丢弃。

**后果**：① 同样的 IOKit/SMC 工作每 tick 做两遍，SMC 连接开关 + 150ms 等待是实打实的常驻开销；② 同一指标两套实现，bug 与口径漂移风险×2；③ v76 注释自述的「两套时间」在数据层仍留尾巴（Swift 侧内存压力/swap/压缩/温度/功耗与 C 侧不同源、不同步）。

### A2. CPU 负载采样三处

1. `frset_stats_data.c` `frset_cpu_sample`（喂 g_snap，菜单栏+面板唯一活数据）
2. `MonitorReader.swift:176 readCPU()`（结果被 A1 覆盖丢弃）
3. `MenuBarIconStyle.swift:253 SystemCPULoad.current()`（host_processor_info，驱动风扇转速）——**第三个实现**

### A3. 整机功耗两种算法（同一物理量）

- Swift：`MonitorReader.swift:502 readPower()` 读 `PowerTelemetryData`（SystemPowerIn / BatteryPower，2026-10-16 本机实证接电 19.5W / 放电 -19.9W）
- C：`frset_stats_data.h:74-75` 电池结构自带 `voltage_mv` / `amperage_ma`（V×A 即功率），但 g_snap 未暴露功耗、部件侧未见使用
- 风险：两条算法数值口径不同时无处对账；面板功耗（Swift）与菜单栏电池（C）天然分裂

### A4. 字节/速率格式化两套（已产生实测差异）

- C：`frset_stats_data.c:320 frset_fmt_bytes` 恒 `"%.1f %s"` → `"512.0 B"` / `"100.0 KB"`
- Swift：`MonitorFormat.swift:8 bytes` 单位 0 取整、≥100 取整、其余一位小数 → `"512 B"` / `"100 KB"`

**同一数值在菜单栏（C 绘）与面板（Swift 绘）字符串不同**——用户此前后馈的「两套时间/两套数值」观感在格式化层的新变种。速率同理（`frset_fmt_rate` vs `MonitorFormat.rate`）。

## C. 操作逻辑 / 设置界面不合理处

1. **「启用系统监测」语义割裂（C1）**：`MonitorPreferences.isEnabled` 只门控 Swift 采样器（MonitorSampler.swift:134/158）；C 引擎/菜单栏合并条完全不受影响。用户关掉「系统监测」，菜单栏照常采照常显示——名称与行为不符。
2. **模块开关三处同名不同权（C2）**：监测设置页（带实时数值）、常规页（checkbox）、右键菜单（勾选）三处写同一死状态（B7）。设置界面「看着能控菜单栏模块」实则不能，真控制在「部件设置」页——入口分散且部分空转。
3. **「显示状态项」空转 + 误导 Toast（C3）**：见 B6。
4. **刷新间隔双配置面（C4）**：监测设置页的「刷新间隔」只管 Swift 采样/面板刷新；菜单栏部件刷新在 C 引擎（0.5s tick + 每模块 updateInterval，配置在部件设置页）——又一处「两套时间」配置面。
5. **双总控并存（C5）**：活的 `monitor.enabled` + 死的 `showSystemStatus`，用户视角是两个都叫「系统监测」的开关。
6. **命令面板设置直达列表过期（C6）**：走 registry 旧 id/旧标题，与侧边栏实际结构双轨；缺「部件设置」与 7 个模块页直达。
7. **功耗/温度数据源分裂（C7）**：面板功耗走 Swift PowerTelemetry（A3），菜单栏电池走 C IORegistry；温度 Swift 6 键 vs C 600 键全扫，面板传感器页与菜单栏传感器部件可能不同值。

## D. 处理建议（按优先级）

**P0（直接删，零行为风险）**
- 删 `frset_barsettings.m`（B1）：67KB 死代码，每包都编译
- 删 `NetworkDiagnostics.swift`（B2）：20KB 死代码（若将来要做网络诊断，从 git 历史恢复）
- 删 B3 休眠链：`MonitorStatusItems.swift`、`Registry.twoLineTitle`、`MenuBarTwoLineView`、StatusBarController 动态项机制（**只保留主图标项**，C 引擎依赖它做参照物）

**P0（消双采样，性能收益直接）**
- `MonitorSampler.sampleOnce` 停采被覆盖字段：CPU/内存/网络/磁盘/电池直接只读 `g_snap`；Swift 侧只保留功耗/内存压力/swap/压缩/温度（A1）。预期去掉每 tick 的 host_processor_info + host_statistics64 + getifaddrs + IOBlockStorage + SMC 连接开关

**P1（对账与语义）**
- 格式化统一：C `frset_fmt_bytes/rate` 改自适应小数（与 MonitorFormat 一致），或面板改调 C 格式化器（A4）
- 「启用系统监测」联动 C 引擎启停，或改名「面板数据刷新」避免歧义（C1）
- 模块开关收敛：三处 UI 删到一处（建议常规页/监测设置页二选一），并让面板模块列表真按它过滤，或明确改为只控面板（C2）
- 删死开关：`showSystemStatus`（B5）、「显示状态项」菜单项（B6）、combinedMode 链（B4）

**P2（结构）**
- 主图标单 Owner：猫覆盖层改由 Swift 侧实现（或 fan/logo 样式让位猫），消除 C 伸进 Swift 按钮子视图树的耦合（A6）
- `SettingsPaneRegistry` 退役：CommandPalette 改读硬编码分类（A7）
- `MonitorCenterView.swift` 更名 `MonitorCenterPresenter.swift`（B8）
