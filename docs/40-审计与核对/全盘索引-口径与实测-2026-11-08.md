# 全盘索引 · 口径与实测（v264，2026-11-08）

> 用户报告（原话）：
> 1. 「它的当前的那个存储清理的那个索引，在状态栏点开的那个监测里面的那个存储，那里面的那个清理的那个索引是不完整，就是没有索引到全盘，整个盘」
> 2. 「包括首页点开的那个上面搜索栏，它的搜索的文件也不是全盘，就比如我搜索 WorkBuddy 里面的当前这个 skill，Image HTML Deck 这个 skill 它就搜不到它的文件夹」

两个问题**根因不同**，分开记。

---

## 一、存储管理：索引为什么只有全盘的四分之一

### 修复前实测（2026-11-08 04:42 前）

| 项目 | 索引算出 | 真实（`du` / `df`） | 差 |
|---|---|---|---|
| `/Applications` | 8.27 GB | **22 GB** | 少 63% |
| `~`（Users） | 34.4 GB | **174 GB** | 少 80% |
| 全盘 | 51.8 GB | **235 GB**（数据卷已用） | 少 78% |
| 节点数 | 157,536 | `find ~` 单个人目录就 **2,048,895** | 少 92% |

### 根因

`DiskIndexScanner.maxDepth = 6`。

深度 6 意味着第 7 层以下的内容整片不算。而：

- `/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/…` 在第 7 层以下
- `~/Library/Application Support/<App>/Caches/<bundle>/…` 常在第 7 层
- 任何 `.app` 的 `Contents/Frameworks/…` 都在第 6 层之后

所以 `/Applications` 只算出 8.27GB —— 恰好是「只统计到 `Contents` 这一层」的量。

**深度本身不影响正确性**（大小是后序遍历累加出来的），它只影响内存。真正的闸门是节点上限（原 30 万），而 30 万连 `~` 的六分之一都不到。

### 修复（v264）

| 项 | 旧 | 新 | 理由 |
|---|---|---|---|
| `maxDepth` | 6 | **64**（等于不限） | 深度不决定正确性，只决定内存；闸门交给 maxNodes |
| `maxNodes` | 300,000 | **4,000,000** | 本机 `~` 单独 205 万条目，全盘约 250 万 |
| `childrenPerDirectory` | 24 | **60** | `~` 下有 30+ 目录，24 会把 `.workbuddy` 折进「其余 N 项」，再也点不进去 |
| 目录 lstat | 每个都 stat | **不 stat**（用 `d_type`） | 省 20% syscall；
目录大小对清理无用（用子树合计） |
| 文件大小口径 | `st_size` | **`st_blocks × 512`** | APFS 透明压缩下 `/System` 逻辑 30GB / 物理 13GB；用 st_size 会让「已索引」虚高、和 df 对不上 |
| 缓存格式 | JSON | **二进制 plist**（回落读旧 JSON） | 40 万节点的树 JSON 要 80MB、解码 2-3 秒 |
| TCC 目录 | 一律跳过 | **有完全磁盘访问权限就扫** | 判据见下 |
| `/System` | 整片排除 | **计入，只排除 `/System/Volumes`** | 系统只读卷 13GB 是真实占用；`/System/Volumes/Data` 是 `/Users` 的另一张脸，算了两遍 |

#### 完全磁盘访问权限的判据

踩了两个坑：

1. 用户级 `~/Library/Application Support/com.apple.TCC/TCC.db` 对未授权进程返回 **ENOENT**（TCC 直接把它藏起来），不是 EACCES —— 拿它判断永远为 false；
2. 直接 `opendir` 相册/邮件目录会弹系统授权框，把扫描流程卡死（v211 已踩过）。

可用判据是**系统级** `/Library/Application Support/com.apple.TCC/TCC.db`：只有 FDA 能打开，拒绝时不弹窗。

### 修复后实测

```
节点      2,486,229（旧 157,536，×15.8）
缓存      58.9 MB（二进制 plist）
总大小    185.1 GB（旧 51.8 GB，×3.6）
truncated false
```

| 项目 | 索引 | 真实 | 结论 |
|---|---|---|---|
| `/Applications` | **22.45 GB** | `du -sh` 22 GB | ✅ 完全对上 |
| `/Users` | 132.4 GB | `du -sh ~` 174 GB | 差 41.6 GB，全是无权限的 TCC 目录 |
| `/System` | 22.5 GB | 系统卷 13 GB | 含 `/System/Applications` 等；系统文件有压缩，仍有残余差 |
| 全盘 | **185.1 GB** | 数据卷已用 235 GB | 差 50 GB |

差额构成（UI 的 `.help` 里也写了）：

- `~/Library/Containers`（沙盒容器）**33 GB** —— 本机 `du` 实测，无 FDA 时被系统拦住
- `~/Library/Mail` / `Messages` / `Pictures` —— 合计不到 100MB（本机）
- APFS 本地快照、交换文件 `/private/var/vm`、文件系统元数据 —— 不在任何目录里，索引天然覆盖不到

授权「完全磁盘访问权限」后重扫，Containers 那 33GB 会进来。

### 顺带修掉的显示问题

- `volumeUsedBytes` 原来用 `attributesOfFileSystem` 的 `systemSize − systemFreeSize`，等于 `f_bavail` 口径，会把 33GB 系统保留算成已用；改成 `statfs` 的 `f_bfree`。
- `/` 是只读系统卷（13GB），用户文件全在 `/System/Volumes/Data`，要读后者。
- 状态行从「跳过 N 处不可读路径」改成 `已索引 185.1 G / 整盘已用 272.1 G` + 节点数，覆盖度一眼可见。
- 新增「去授权」直达按钮（`x-apple.systempreferences:…?Privacy_AllFiles`）。

## 二、搜索：Spotlight 压根没索引那片

### 实测证据

```
$ ls -d ~/.workbuddy/skills/*html*
/Users/sunyiyang/.workbuddy/skills/image-html-deck

$ mdfind "kMDItemFSName == '*image-html-deck*'cd"
（空）

$ mdfind -onlyin ~/.workbuddy "kMDItemFSName == '*image*'cd"
（空）
```

不是查询写错了，是**这条路径不在 Spotlight 库里**。macOS 的 Spotlight 默认不索引：

| 盲区 | 本机条目数 |
|---|---|
| `~` 下以 `.` 开头的隐藏目录 | 约 80 万（`.workbuddy` 16.1 万、`.gemini` 9.7 万、`.lmstudio` 8.8 万…） |
| `~/Library` | 约 100 万 |
| `/Applications/**/*.app/Contents/**`（47 个 app） | 8.1 万 |
| `/usr/local`、`/opt` | 40 |

`mdfind -onlyin ~/Library` 同样返回空 —— `~/Library` 整片不索引。

这几处恰好是开发者文件最密集的地方，于是「搜不到」成了常态。

### 方案：自建全盘文件名索引（`FileNameIndex.swift`）

对标 `locate(1)`，但不依赖 root、不改系统设置：

1. 后台遍历盲区根，把所有路径写进**一个平坦字节池**（`\0` 分隔，164MB）；
2. 查询时 `mmap` 映射，用**大小写不敏感的 Boyer-Moore-Horspool** 扫池，
   命中点向前后回溯到 `\0` 取完整路径；
3. 落盘缓存，只在首次（或点「重建」）生成。

设计取舍：

| 决定 | 理由 |
|---|---|
| 只索引盲区，不索引整盘 | Spotlight 对可见目录已经覆盖得很好（mdfind 实测 0.15s），重复索引 350 万条只会让磁盘和内存翻倍 |
| mmap 而不是内存数组 | 164MB 常驻堆内存会实打实挤占用户 App；mmap 的冷页由系统按需回收 |
| 只存一份原样路径 | 再存一份小写副本会让 164MB 变 328MB；大小写不敏感靠搜索时的 ASCII 折叠表 |
| ASCII-only 小写 | `String.lowercased()` 对某些 Unicode 字符会改变字节长度，而我们依赖「折叠前后字节数一致」 |
| 零常驻 | App 启动、面板打开都不建索引；只有用户真的输入了文件查询才触发 |

### 实测

| 阶段 | 数据 |
|---|---|
| 建索引耗时 | **14 秒**（124 万条 → 164.3 MB） |
| `image html deck` | 8 条，**44 ms**（优化前 453 ms） |
| `workbuddy skill` | 8 条，**162 ms** |
| `cargo` | 8 条，**37 ms** |

### 三个必须解决的坑

**① 空格 vs 连字符（不然永远是「没有匹配的文件」）**

`FuzzyMatcher` 是子序列匹配：`image html deck` 里的空格在 `image-html-deck` 里不存在 →
**必然不命中**。修之前哪怕索引里明明有这条，UI 也一直显示「没有匹配的文件」。

修法：精排前把查询的空格去掉（`imagehtmldeck`），mdfind 的通配符版同理。

**② 候选顺序（`~/.workbuddy/skills` 在第 17947 位）**

池是 DFS 顺序，前面堆着 `.cc-switch` / `.gemini` / `.trae-cn` / `.lmstudio` 下几千条
`skills/research-router/records/…` 长路径。`~/.workbuddy/skills` 在**全部**合格项里排
第 17947 位，但在**短路径**（≤120 字符）里只排第 1417 位。

修法：候选分两档（短路径优先计数），收集 2500 条后按「路径深度 → 长度」重排。

**③ 每条命中都造 String（453ms 的来源）**

`skill` 在池里命中 9.5 万次，其中 2.6 万条通过 AND 过滤。每次命中都
`String(decoding:)` + `lowercased()` 要 552ms（脚本实测）。

修法：AND 过滤改成**字节级区域匹配**（`regionContains`），不再造 String。

### UI

- 「文件」分组下方常驻一行索引状态：`全盘索引 1,240,856 项 · 22 分钟前建立 · 含隐藏目录 / ~/Library / .app 内部` + 「重建」
- 未建立时显示「Spotlight 不索引 ~/Library、隐藏目录…」+「建立全盘索引」
- 建索引中显示进度（已收录 N 项）
- **建完后自动重跑当前查询** —— 否则用户第一次搜时索引还在建，看到"没有匹配的文件"就走了

## 三、排障入口

```
kitnest://fileindex?q=image%20html%20deck          # 查询并打日志（含耗时）
kitnest://fileindex?q=image%20html%20deck&build=1  # 强制重建后再查
kitnest://storage?scan=1                           # 触发一次全盘扫描
kitnest://storage?drill=Users                      # 打开并下钻一层
```

搜索面板自动填词（自动化截图用）：

```
defaults write com.sxyq.frsetnext probe.searchQuery -string "image html deck"
```

（`FRSET_SEARCH_PROBE` 环境变量在本机 `open --env` 传不进 App，实测无效，所以加了 UserDefaults 兜底。）

## 四、索引文件位置

| 索引 | 路径 | 大小 |
|---|---|---|
| 存储管理 | `~/Library/Application Support/FrsetNext/disk-index/index-fullDisk.json` | 58.9 MB（二进制 plist） |
| 文件名 | `~/Library/Application Support/FrsetNext/file-index/names-v1.idx` | 164.3 MB |

两个都是「打开对应界面 / 首次搜索才加载」，平时不占资源。存储管理的「设置 → 清除索引缓存」可删；文件名索引在搜索面板状态行点「重建」会重写。
