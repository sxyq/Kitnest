# 截图点击链路实测 · 2026-11-11

> 零代码改动，全部为外部测量：`open kitnest://capture` 触发后，用 `CGWindowListCopyWindowInfo` 每 2ms 轮询，记录「触发 → 覆盖层窗口出现」的端到端时间；另取应用自身已有的 `截图快照冻结完成` 日志作为内部阶段耗时。

## 一、端到端：触发 → 可框选

| 轮次 | 延迟 | 说明 |
|---|---|---|
| 冷启动第 1 次 | **> 4000ms（超时）** | 首次触发被吞掉，覆盖层未出现；第 2 次才恢复 |
| 冷启动第 2 次 | 724ms | ScreenCaptureKit 首次握手 |
| 冷启动第 3 次 | 272ms | 已热身 |
| 热身 1 | 391ms | |
| 热身 2 | 171ms | |
| 热身 3 | 182ms | |
| 热身 4 | 144ms | |

- 热身稳态：**144 / 171 / 182 ms**，中位数约 **175ms**。
- 冷启动首击：**> 4s 或被吞**；第二击 724ms。这是用户「第一次按没反应、要再按一次」的直接证据。

## 二、内部阶段：快照冻结

应用已有日志 `截图快照冻结完成 Nms`（`ScreenshotManager.swift:541-543`），取最近 12 次：

```
173  114  85  79  93  81  76  91  62  79  372  198
```

- 中位数 **82ms**，P90 **198ms**，峰值 **372ms**。
- 与端到端 272ms 那次对齐：冻结 198ms + 后续 74ms（TCC 探测 + `NSApp.activate` + 覆盖层建窗）。

**归因比例（热身态）**：冻结帧约占 **55–70%**，覆盖层构建与激活约占 **30–45%**。

## 三、冻结阶段为什么慢（读码结论）

| 位置 | 行为 | 成本 |
|---|---|---|
| `ScreenshotManager.swift:589-596` | `for screen in NSScreen.screens` **串行** `await captureScreenAdaptive` | 多屏线性叠加，双屏≈×2 |
| `ScreenshotManager.swift:168-190` | 自适应通道：SCK 优先，失败回退 legacy / `screencapture` | 回退路径单次 ≈200ms |
| `ScreenshotManager.swift:52-77` | 兜底起 `/usr/sbin/screencapture` 子进程，写临时 PNG 再 `Data(contentsOf:)` + `CGImageSourceCreateImageAtIndex` 解码 | 进程启动 + 全屏 PNG 编解码（3420×2224）|
| `ScreenshotManager.swift:513-518` | `startCapture` 先 `await ensureScreenRecordingPermission()`，才进 `beginCapture` | 同步 TCC 探测，落在按键到冻结之间 |

## 四、提交阶段（松开鼠标 → 出图）

`commitRegion`（`ScreenshotManager.swift:598-634`）在后台队列**又整屏抓一次** `NativeRegionCapture.capture`，然后裁切。也就是说一次框选要抓两遍全屏：一遍冻结预览，一遍出图。日志里 `选区截图：797×784pt → 1596×1570px` 即为第二次抓取的结果。

## 五、空闲开销（`sample` 3 秒）

```
mach_msg2_trap        10616   ← 主线程 runloop 空转等待
__workq_kernreturn     7877   ← 后台线程空闲
__semwait_signal       2601   ← 线程池等待
argb32_image_mark_argb32    6
```

结论：**空闲态没有自旋、没有轮询热点**，采样几乎全部落在等待系统消息上。空闲 CPU 不是问题，问题集中在「按键后的那 150–400ms」和「提交时的第二次全屏抓取」。

## 七、场景采样（`sample` 2 秒）

| 场景 | 最热栈 | 判读 |
|---|---|---|
| 空闲 | `mach_msg2_trap 10616` / `__workq_kernreturn 7877` | 全在等消息，无自旋 |
| 主面板打开后 | `__workq_kernreturn 16080` / `mach_msg2_trap 12791` / `__select 453` | 面板静止后立即回到空闲，无持续重绘 |
| 截图覆盖层弹出后 | `__workq_kernreturn 17085` / `mach_msg2_trap 13783` / `rgba32_sample_rgba32 5` | 覆盖层静止不重绘，只有交互帧才画 |

结论：三态都干净。**成本全部集中在「瞬间」**——按键后的 150–400ms、框选拖拽的每帧、提交时的第二次全屏抓取；不是持续占用。

## 八、测量方法的两点说明

1. 触发用的是 `open kitnest://capture`（LaunchServices），比真实 `⌥S` 多一次 URL 分发（约 10–30ms），所以端到端数字偏保守。
2. 本机未给终端「辅助功能」权限，脚本发的 `Esc` 无法收起覆盖层，多轮测试会叠加窗口。前两轮（>4s、724ms）因此可能偏高；热身四轮（391/171/182/144ms）是在叠加 1–2 层覆盖层的情况下测的，仍稳定在 150–180ms。
