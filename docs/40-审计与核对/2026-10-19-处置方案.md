## A. 重复实现解决方案（分期执行）

总纪律（沿用 CONTRACT）：**一期只改一个变量，改完构建+实测+记录，再开下一期**；每期结束是可运行状态，禁止多症齐改。

### A-0（第 0 期：只删不改，零行为风险）——删死代码

| 对象 | 动作 | 验证 |
|---|---|---|
| `Sources/FrsetStatsBar/frset_barsettings.m`（67KB） | 整文件删除；`frset_barwidgets.h` 去掉 `FSBarSettingsOpen`/`FSBarSettingsOpenModule` 声明 | 构建通过；`nm` 无 FSBarSettings 符号 |
| `Sources/Features/Monitor/NetworkDiagnostics.swift`（20KB） | 整文件删除（零外部引用实证） | 构建通过 |
| `MonitorStatusItems.swift` 双排项链 | 删 `MonitorStatusItems.swift`；`Registry.StatusItemDescriptor.twoLineTitle` 字段移除；`StatusBarController` 动态项机制（twoLineView/overflow/sync/位置保存恢复）整段删除，**只保留主图标项**（C 引擎 `FSBarSetMainItem` 依赖它） | 构建通过；菜单栏合并条不变；主图标左键仍开面板 |
| `MonitorCenterView.swift` | 更名 `MonitorCenterPresenter.swift`（现仅存 presenter，名不副实） | 构建通过 |

删除规模约 96KB 源码，编译单元与维护面直降。**预期风险=0**（全部零调用方或已停用）。

### A-1（第 1 期：消双采样）——数据层单轨

目标：`MonitorSampler` 不再跑被覆盖的字段，Swift 侧只采 C 层没有的。

- `sampleOnce()` 删除 `reader.readResult()` 中的 CPU/内存/网络/磁盘/电池读取（`MonitorReader.readCPU/readMemory/readNetworkCounters/readDiskRate/readBatteryLevel` 整体停用），核心指标**只读 `g_snap`**（已经是 v76 的覆盖逻辑，改为不采而非采完丢弃）。
- 保留 Swift 独占字段：功耗（`readPower`）、内存压力、swap、compressed、温度键集——**明确注释这三个字段是 Swift 侧唯一采集点**，防止后人再"统一"回 C 层。
- 同时处理 A2/A3：`SystemCPULoad`（风扇转速）改读 `g_snap.cpuUsage`（第三个 CPU 采样器消失）；功耗二选一——建议面板功耗继续用 PowerTelemetryData，但在注释与文档登记「C 层有 V×A 备胎，数值不一致时以本实现为准」。
- 验证：设置页「已采样 N 次」正常涨；面板数值与菜单栏部件**同一 tick 同一值**（用户此前后馈的「两套时间」彻底闭合）；CPU 占用（活动监视器看 FrsetNext）应明显下降。

### A-2（第 2 期：格式化对账）——消除同值两样貌

- C `frset_fmt_bytes/rate` 改为与 `MonitorFormat` 相同的自适应精度（B 取整、≥100 取整、其余一位小数）；或反向——面板格式化全部改调 C（经桥接头暴露 `frset_fmt_rate`）。
- 推荐前者（C 跟 Swift，Swift 是 UI 侧的事实标准），改完用一组固定值对照：512B / 1536B / 102400B / 1048576B 在菜单栏与面板字符串一致。

### A-3（第 3 期：设置界面收敛）——死开关与双轨清理

- 删死开关：「常规 → 功能 → System Monitor」（`showSystemStatus` 无读取方）；右键菜单「显示状态项」（`menuBarIconsVisible` 空转+Toast 误导）；合并模式链（`combinedMode`/`visibleStatusItemIDs`/`toggleMonitorCombinedAction`）。
- 模块开关三处收敛为一处：保留「监测设置」页的模块开关（带实时数值），删常规页 `monitorToggle` 与右键「显示项」子菜单；同时让面板/设置模块列表**真正按它过滤**（`StatsModulePage`/popout 打开时校验 `isModuleEnabled`），否则改名「面板模块显示」避免误导。
- 「启用系统监测」补 C 引擎联动：关闭时 `StatsBarEngine.stop()`（或至少停止合并条刷新），开启时恢复；改名备选「面板数据刷新」。
- `SettingsPaneRegistry` 退役：`CommandPalette` 的设置直达改读硬编码 `SettingsCategory` + 监测区（补「部件设置」与 7 个模块页直达），随后删 Registry 的 `SettingsPaneRegistry` 段与 9 处 register 调用。

### A-4（第 4 期：主图标单 Owner）——解跨语言耦合

- 目标：主图标按钮只有**一个**绘制方。两个方向二选一：
  - 方向①（推荐）：小猫覆盖层逻辑从 C 搬到 Swift（`FSRunCatEnsureMainIconOverlay` 的挂载/隐藏/速度档改为 Swift 侧 `MenuBarIconStyleApplier` 统一管理），C 只保留帧数据表 `frset_runcat_frames.c` 经桥接头供 Swift 取帧；
  - 方向②：保留 C 覆盖层，但把「隐藏 button 全部子视图」改为**只隐藏 Swift 登记的图标视图**（白名单制），并去掉 `MenuBarIconStyleApplier` 的 fan 子视图路径（fan 与猫二选一由设置决定）。
- 本期会碰 v82 修过的区域，**必须先复现「两只猫」再改**（钩子开启+截图三帧差分）。

## B. 后续接入开源项目的防复发规范

本次事故（双数据层/双设置窗/双状态栏）的根因不是「接入」本身，而是**接入时没有先划边界**。把以下 5 条写进 `apps/FrsetNext/CONTRACT.md`（或 docs/00-总览/工程结构与构建.md），作为强制流程：

1. **接入前先画能力重叠图**：新开源项目落地前，列一张表——「它提供的能力 × 本仓现有实现」。只要出现同一能力两行，当场裁决：替换 / 并列（明确谁活跃谁休眠）/ 拒绝接入。**不允许「先接进来以后再说」**（本次 C 引擎接进来时，Swift Monitor 全套没退役，也没有写下休眠标记，才有后来的双轨）。
2. **接入即配「退役清单」**：接入生效的同一次提交里，被取代的本仓实现必须进入退役清单（注释顶灯 + 文档登记），并**在代码里留机械可判的标记**（如 `// DEPRECATED-2026-10-19: 被 FrsetStatsBar 取代，勿删除——C 引擎依赖其主图标项`）。本次扫描里 `MonitorStatusItems` 的退役只存在于 commit message，代码内无标记，导致后人（含 AI）无法判断它是死是活。
3. **桥接层单一入口**：跨语言/跨模块只允许一个桥（现在是 `FrsetStatsBar.h` + `StatsBarEngine.swift`）。开源项目的 API 不得被各模块直接散调；本次 `FSBarCfg*` 被 MonitorWidgetsPane 直接散调 20+ 处，虽是同侧，也应由 StatsBarEngine 出 façade。
4. **数值口径登记表**：任何「同一物理量两种算法」（功耗、温度、负载、格式化）必须登记到一张表（指标 / 活跃算法 / 备用算法 / 不一致时以谁为准）。没有登记表的第二种算法不许进主干。
5. **接入后 30 天清理窗口**：接入提交后，被取代实现的删除工作排进当期任务（本次是 v42 停用 → 3 天后扫描才发现整套还在编译）。停用不满一个清理窗口的，CI/check.sh 给出警告清单。

## C. UI 组件审核报告

### C-1. 样式体系全景（7 种卡片/背景习惯并存）

| # | 体系 | 定义位置 | 使用方 | 观感 |
|---|---|---|---|---|
| 1 | `.popover` 玻璃窗 + **白色卡片** | FloatingPanel.swift:48-56（v74 统一）+ 面板内各卡 | **主面板** | 玻璃底上漂白卡 = 用户说的「白框+玻璃」✓（2026-10-19 实拍确认） |
| 2 | `.popover` 玻璃窗（无白卡） | MonitorPopoutWindow.swift:99 | **性能监测独立窗** | 纯玻璃 ✓ |
| 3 | `LiquidGlass` 统一封装（26+ 真 NSGlassEffectView） | Core/LiquidGlass.swift | **仅 FloatingPanel.embed 一处** | 纯玻璃（但几乎没人用） |
| 4 | `Theme.cardBackground` = controlBackgroundColor 60% 白卡 | Support.swift:138 + SettingsComponents.swift | 设置窗 3 页（部件设置/数据/常规） | **浅灰底+白卡，窗口本身不玻璃**（2026-10-19 实拍确认） |
| 5 | `Color.primary.opacity(0.02~0.08)` 灰卡 | JSONInspector / TransferDock / CloudLinkBar / PreviewPopover 各自为政 | 4+ 处 | 半透明灰卡，圆角 3~14 不一 |
| 6 | `windowBackgroundColor` 不同透明度（0.55/0.92/0.94） | FloatingClipboard / EasterEgg 对话框 / PanelRootView 工具条 | 3 处 | 近纯色 |
| 7 | SwiftUI `.regularMaterial` / `.ultraThinMaterial` 直用 | PreviewPopoverContentView:632 / MenuBarIconEasterEggDialogOverlay:159 | 2 处 | 材质但非系统 popover 玻璃 |

**结论**：用户观感完全成立且已实拍对上——**设置窗是唯一的主表面却不用玻璃**（纯色底+白卡，「背景材质」当前停在「纯色卡片」）；主面板是玻璃但上面仍漂白卡（白框+玻璃）；性能独立窗是纯玻璃；其余 4 类习惯散落。同一 App 三个主表面三种语言。

### C-2. 「首页打开之后，不是首页，是设置界面」定位

**已逐条实证排除**（2026-10-19，部署版 /Applications/FrsetNext.app + URL scheme 实拍）：
- 主图标左键 → `panel.toggle(atAnchor:)` 接线正确，弹出的是**主页**（搜索框+日历+剪贴板历史，实拍确认）；
- 面板「性能监测」页 → 完整监测仪表盘（CPU 70%/每核条形/负载/高占用进程），不是设置界面；
- URL scheme / 默认热键 / 小猫覆盖层事件（猫视图无鼠标处理，不吞点击）/ 设置窗自动弹出——全部无罪。

**定位到的真实问题（按可能性排序）**：
1. **面板重开不落首页**：`MonitorCenterPresenter` 是进程级单例，`page` 仅 init 时设为 `.home`，**面板关闭不复位**。用户上次停在「性能监测」→ 关面板 → 再点主图标 → 落在性能监测页（模块卡片窗，观感即「设置界面」）。**这是与用户描述最吻合的路径**。
2. 设置窗侧边栏的「主页」是**不可点的分组标题**（v41 设计：主页=6 类设置的集合），用户点它无反应，容易读成「没有首页」。
3. 面板右上角唯一的图标是**齿轮（开设置窗）**，与三页签并列，误点即得设置界面（设计如此，但视觉上缺少分隔）。

**建议**：`hide()` 时 `selectHome()` 复位（或产品上明确「记忆上次页」——需用户裁决）；侧边栏「主页」组首行「常规」即设置首页，可将组标题改为「设置」消除歧义；面板齿轮移至页签行外或加 tooltip。

### C-3. 组件一致性整改（按面收敛）

1. **设置窗材质统一**：`SettingsRootView` 背景与卡片改用 `LiquidGlass`/`.popover` 体系，「背景材质」的「纯色卡片」降级为次级选项或删除（与主面板/性能窗同语言）；`Theme.cardBackground`（白 60%）与 Midnight 深卡二合一对 `LiquidGlass` tint。
2. **设置组件全员化**：现仅 3 页用 `SettingsSection/GroupBox/Row`，另外 8 页（搜索/AI/剪贴板/工具/快捷键/截图/个性化/关于）各自为政——全部改用共用组件（本期只换容器不改内容，一个变量）。
3. **散点灰卡收编**：`Color.primary.opacity(0.0x)` 卡片统一为 `Theme.cardBackground`（或 LiquidGlass tint 卡），圆角统一 `Theme.cornerRadius`（现 3/4/5/6/7/9/12/14 八种）。
4. **窗口 chrome 统一**：`OfficialWindowChrome` + `RoundCloseButton` 覆盖全部自有窗口（现 JSONInspectorWindow/ClipboardPreviewWindow/FloatingClipboardWindow 各自实现）。

### C-4. 验证方式（无鼠标环境）

每期改完：`open frsetnext://panel` / `frsetnext://settings` / `frsetnext://monitor` 三连发 + 截屏三帧差分；材质类改动必须同时截**浅色/深色/Midnight** 三种外观（`AppearanceManager` 可程序化切换）。
