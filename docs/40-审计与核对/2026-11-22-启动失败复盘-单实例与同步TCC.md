# 复盘：2026-11-22「点了 App 打不开」——单实例锁、僵尸进程与启动路径上的同步 TCC

> 级别：P0（用户完全无法使用）
> 影响面：本机安装版；用户反馈「甚至无法打开了，并且 app 卡死」「点了之后它无法启动，这是最大的问题」
> 结论：**不是一次代码写错，是三类“看起来无害”的写法叠在一起**。下面每一条都写成可检查的规则。

## 1. 用户看到的现象

- 点菜单栏图标 / 双击 App：没有任何反应，也不报错。
- 有时进程在活动监视器里还活着，但界面永远不出现。
- 强杀、重装、重启 App 都无效；日志里只剩一行
  `已有实例在运行（pid=XXXXX）→ 本实例退出`，或者干脆停在
  `Bootstrap: appTools begin` 之后没有下文。

## 2. 三条独立成因（任一条都足以让 App 起不来）

### 2.1 单实例检查把“卡死的自己”当成“健康的自己”

```swift
// 旧实现（错误）
let others = NSRunningApplication.runningApplications(withBundleIdentifier: bid)
    .filter { $0.processIdentifier != getpid() }
if let existing = others.first {
    existing.activate(...)
    NSApp.terminate(nil)      // ← 无条件自杀
}
```

- 判据是「同 bundle 有没有别的进程」，**没有任何活性判断**。
- 旧实例主线程被堵死时，它不会退出，也不会响应 activate；新实例却老老实实自杀。
- 结果：一个卡死进程 = 这台机器上再也打不开这个 App。重装也没用（进程还在）。

### 2.2 僵尸进程（defunct）会被算成“已有实例”，而且杀不掉

- 进程被 `kill -9` 后，如果父进程没有 `wait`，内核保留 pid → 僵尸。
- 僵尸：`kill(pid, 0)` 返回成功、`NSRunningApplication` 照样列出、`forceTerminate()` 无效。
- 于是 2.1 的自杀逻辑永远成立，用户侧表现就是「怎么点都不开」。
- 本机实测：`kill -9 8677` 返回 0，但 pid 依然存在，`pgrep` 仍列出 `8677 Kitnest`。

### 2.3 启动路径上有两次同步 TCC 查询

```swift
// 旧实现（错误）：属性初值就是一次同步 TCC 往返
@Published public private(set) var hasPermission: Bool = CGPreflightScreenCaptureAccess()

// init 里又来一次
Log.info("Capture", "屏幕录制权限启动实况：\(CGPreflightScreenCaptureAccess() ? ... )")
```

- `CGPreflightScreenCaptureAccess()` 是**同步 XPC 到 tccd**。
- `ScreenshotManager` 在 bootstrap 的 `appTools` 阶段被构造 → 主线程阻塞在 tccd 上。
- 本机 17:23 真实卡过一次 260s+；抓到的栈是
  `App.main → NSApplication.init → TCCAccessLaunchDisclosurePromptIfNeeded →
   tccd_send_message → mach_msg`，以及另一个进程停在 `Bootstrap: appTools begin`。
- 也就是说：**tccd 状态不好时，这个 App 会在“还没画出任何界面”之前挂死**。

## 3. 为什么没被拦住

| 缺口 | 说明 |
|---|---|
| 没有冷启动闸门 | 构建完只验证「改动生效」，没有一条“从零启动一次并确认 `启动完成`”的硬性检查 |
| 改动集中在 UI/性能 | 单实例与权限检查属于“六个月没动过”的启动代码，评审注意力不在那 |
| 只在“已有实例在跑”的环境里测 | 构建脚本会提示「旧版本正在运行，重新打开即新版」，于是从未验证过**没有健康实例**时的冷启动 |
| 僵尸/卡死状态不可见 | 这两个状态在活动监视器里和正常进程长得一样，日志又只有一行“已有实例在运行” |

## 4. 修复（v282，已落地）

1. `InstanceLock`：`instance.lock` 上的排他 `flock` 成为「谁是唯一实例」的**唯一权威**。
   fd 是内核对象，进程一死就释放；僵尸不持锁 → 天然被排除。
2. 抢不到锁 → 读锁文件里的 pid；若 `logs/main-thread.hang` 120s 内写过（主线程被堵）
   → `SIGKILL` 接管，2s 内重试抢锁。
3. 僵尸判定：`proc_pidinfo` 的 `pbi_status == SZOMB(5)`，只作附加信号（沙箱下可能读不到）。
4. 启动路径禁止同步 TCC：`hasPermission` 初值改 `false`，init 里的权限探测丢后台队列，
   查完回主线程发布。**启动流程不再等 TCC。**

## 5. 铁律（写进 AGENTS.md 与会话记忆）

1. **启动路径（`applicationDidFinishLaunching` 之前到 `启动完成` 之间）不允许任何同步 TCC / 同步 XPC / 同步等待。**
   典型禁用：`CGPreflightScreenCaptureAccess`、`CGRequestScreenCaptureAccess`、
   `AXIsProcessTrusted`、`SCShareableContent`、`AVCaptureDevice.authorizationStatus`、
   `NSAppleScript`、`Process.waitUntilExit`。
   一律：后台队列查询 → 回主线程发布。
2. **单实例判定必须用内核对象（flock / `flock`+pid 文件），不得只用进程列表。**
   进程列表在「卡死」和「僵尸」两种状态下都会说谎。
3. **禁止无条件 `NSApp.terminate(nil)`**：退出前必须能回答“那个实例现在是活的吗”，
   答案不确定时选择**接管**而不是自杀（菜单栏重复一秒，比打不开一小时轻）。
4. **每次构建后必须冷启动冒烟**（见 `tools/launch_smoke.sh`）：
   先把本机所有 Kitnest 进程杀掉，再启动，确认日志出现新的 `启动完成` 且没有
   `已有实例在运行` / `应用退出`。**这条不通过不算改完。**
5. **卡死要留证据**：看门狗在阻塞 > 2s 时自动 `sample` 自己，栈落
   `logs/hang-*.txt`；没有栈的“卡死”复盘等于没做。

## 7. 补记：闸门自己的两次误报（比 bug 本身更值得记）

`launch_smoke.sh` 上线后连报两次「✗ 冷启动失败」，两次都不是 App 有病：

**第一次**：日志只有 `已有实例在运行（pid=8677）→ 应用退出`，没有 `获得实例锁`。
看起来像修复没生效。查下来锁文件里写的是 `62967`——那是 19:41 正常启动的实例，
`sysctl` 读到 `p_stat = 2 (SRUN)`，**活得好好的**。App 拒绝启动完全正确：
同一时刻确实已经有一个自己在跑。

**第二次**：脚本先 `pkill -9 -x Kitnest` 再启动，仍然失败。
原因是这个执行环境里 `kill -9` 对那个进程返回成功但进程不消失（沙箱限制），
`pkill` 干脆匹配不到。**闸门把「环境杀不掉」误判成了「App 有病」。**

这两次暴露了两条比 bug 更重要的纪律：

1. **闸门必须能区分「环境不允许」和「产品有问题」**。
   现在的 `launch_smoke.sh`：杀不干净就打印
   「⚠ 跳过：仍有一个活着的实例握着实例锁……」并 `exit 2`；
   只有真的「拿到锁却起不来」才 `exit 1`。误报的闸门最后一定会被忽略。
2. **单实例拒绝启动时，日志必须写清「谁握着锁、它是否活着」**。
   上面第一次的日志写的是 `pid=8677`（`NSRunningApplication` 列表里随便挑的一个僵尸），
   真实持有者是 `62967`——一条误导性日志能让排查多花半小时。

顺带保留了两处防御（不是本次根因，但堵的是更难查的形态）：
`open(... O_CLOEXEC)` 防止锁 fd 被 helper 子进程继承；「持有者不是活着的同 bundle 实例
就回收残留锁」防止继承残留把 App 永久锁死。
