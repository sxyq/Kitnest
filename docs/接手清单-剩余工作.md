### 三个版本的称谓（以后一律用这三个词，不要混用、不要自造）

| 称谓 | 指什么 | 在哪 |
|---|---|---|

### 核心约束：菜单栏监控**唯一一套 = STATS**

- 菜单栏的监控呈现**只允许一套**，即 **STATS 合并条**（`Sources/FrsetStatsBar/` 引擎 + `StatsBarEngine` 桥）。
- **禁止**再引入第二套菜单栏监控——官方原版那 4 个独立原生项（网速/CPU/RAM/SSD）、任何自绘状态项都算第二套。
- **三道防线（v43 已落地，勿删）**：
  1. app **单实例**：`AppDelegate.enforceSingleMenubarOwner()`——多开实例会各建一套合并条；
  2. `StatsBarEngine.start()` **幂等**：重复调用不再创建第二个状态项；
  3. 检测**官方原版在跑** → Toast 提示退出（原版的注入引擎也会画一套，且与本 app 共用
     `~/Library/Application Support/FrsetStats/` 下的 `widgets.plist` 与 `engine.log`）。
- **部件形态**：一个合并条状态项内绘制多个**独立分隔**的部件（CPU 折线 / RAM 柱状 / SSD / 网络速度 / 传感器…），
  点某个部件按其位置判定模块并打开主面板对应页。这就是"一个一个单独"的既定形态，**不要**合成一个总标签，
  也**不要**拆成多个独立状态项（那样菜单栏更长且更难对齐）。

## 1. 你必须知道的环境事实（否则会踩坑）

1. **原版 Frset 是沙箱应用**，拷贝到 `/tmp` 直接运行会被拒（`sandbox_extension_issue_file_to_process failed`）。要程序化启动它，必须用「迷你 .app 引导」：把脚本写进 `/tmp/Xxx.app/Contents/MacOS/runner`（配 `Info.plist`、`LSUIElement=true`），执行**`/Applications/Frset.app/Contents/MacOS/Frset`**，再 `open -n`。
2. **App 有单实例守卫**：已有实例运行时，新实例会 `exit 0` 静默退出。注入采集才需要短暂停止原版；普通读取文档/机器码或使用当前可用的原生 UI 工具无需停原版。采集结束必须结束注入实例，再 `open -a /Applications/Frset.app` 恢复用户实例；仅调用 `open -a` 无法证明注入实例已被替换。
3. **历史 WorkBuddy 的 `screencapture` 失败**（`could not create image from display`），当时使用注入探针的 `CALayer renderInContext`。当前 Codex 原生截图已成功保存重建通用页，不能沿用旧限制推定当前没有权限。不同采集方式的白底/灰底色差须分开解释，最终视觉对照应使用相同方式。
4. 历史采集的合成键盘/鼠标事件未能驱动目标 SwiftUI 窗口；AppKit `performClick:` / `sendEvent:` 曾可用。当前 AX 已成功打开重建设置并确认五页签；不得将旧工具失败扩大为全部 UI 工具均不可用。
5. **`NSClassFromString` 只证明「类存在」，不证明「能无参构造」**——实测 13 个 Controller 的裸 `init` 全部崩溃。
6. **本机编译内存是瓶颈**：16GB + swap 常近满。`build.sh` 已改为 `-O -no-whole-module-optimization`，124 文件约 3 分钟；**typecheck 约 55 秒，迭代优先用 typecheck**。
7. **A6000 服务器是 Ubuntu/Linux，不能编译 macOS App**（无 macOS SDK / AppKit / SwiftUI），不要在该服务器编译；旧记录的 `ssh a6000` 也不能作为已确认可用的连接别名。
8. `ps`/`top`/`launchctl` 与 PyPI 限制是历史会话现象，不代表当前工具权限。PID 会变，需要定位原版时用 `pgrep -f '/Applications/Frset.app/Contents/MacOS/Frset'`；本轮文档整理未操作应用或服务器。
9. **程序化唤起 FrsetNext 用 URL scheme**（2026-10-16 新增，等价原版 `showSettingsWindow:` @objc 入口）：`open "frsetnext://settings?pane=general|search|tools|shortcuts|about"` 与 `open "frsetnext://statistics"`。辅助功能/录屏权限缺失时这是唯一可靠的窗口唤起路径。改 CFBundleURLTypes 后需 `lsregister -u <app> && lsregister -f <app>` 重新注册，且 app 要重启。
10. **窗口布局纪律（防回归，specs/07 §4.3）**：SwiftUI App lifecycle 下 `NSHostingView` 会把根视图 fitting size 折成窗口尺寸请求；根视图必须固定尺寸（设置/统计 = `.frame(width: 800, height: 530)`），**禁止** `.frame(maxHeight: .infinity)` 作根视图，否则窗口被反复请求撑到内容自然高（实测 1554pt），触发 `NSGenericException`（"more Update Constraints in Window passes than there are views"）进程即死。窗口控制器不设 `setFrameAutosaveName`（原版窗口固定尺寸）。
11. **`@State` 宏不可用**：本机 Command Line Tools 缺 SwiftUIMacros 插件，`@State` 编译报 "plugin for module 'SwiftUIMacros' not found"；全工程用 `@Stored`（`Sources/Core/StateCompat.swift`）替代。同理 SDK 的 `application:openURLs:` 被 Swift renamed import 为 `application(_:open:)`，参数是 `[URL]` 不是单个 `URL`。
12. **屏幕录制授权必须用固定证书签名（2026-10-18 根治）**：用户实障"系统设置里授权了 FrsetNext，app 却提示没授权、截不了屏"。彻底排查结论：**ad-hoc 签名（`codesign -s -`）的 designated requirement = `cdhash H"<二进制内容哈希>"`**（`codesign -d --requirements -` 可验证）——TCC 授权记录绑这个哈希，而每次重新编译内容必变 → 哈希变 → 授权失效 → app 内 `CGPreflightScreenCaptureAccess()` 返回 false → 弹"需要屏幕录制权限"。**与代码逻辑无关**（截图失败路径不会误报未授权，已排查排除）。修复：钥匙串自签证书 **FrsetDev**（openssl 生成：keyUsage=critical,digitalSignature + EKU=codeSigning + basicConstraints=CA:FALSE；`security import` 证书与私钥 + `security add-trusted-cert -d` 用户级信任——注意本机 openssl 是 LibreSSL 无 `-legacy`，p12 与钥匙串 MAC 不兼容，须证书/私钥分别导入）。build.sh 改为 `-s "FrsetDev"`（无证书时回退 ad-hoc 并打醒目警告）。证书签名的 requirement = `identifier "com.sxyq.frsetnext" and certificate leaf=H"2efbee..."`——**与内容无关，授权一次后重新构建保留**（2026-10-18 实测：全新二进制启动实况"已获得"）。若哪天真出问题：跑 `apps/FrsetNext/修屏幕录制授权.command`（`tccutil reset ScreenCapture com.sxyq.frsetnext` + 重启 + 重新授权一次）。证书在 `~/Library/Keychains/login.keychain-db`（CN=FrsetDev），换机器/清钥匙串后需按上述参数重建，或找 `/tmp/frset_dev.key` + `/tmp/frset_dev2.crt`。
13. **“已损坏，无法打开”根因 = 非原子部署（2026-10-18 v31 根治）**：用户反复遇到“点开 app 提示已损坏”（废纸篓里留有 `FrsetNext.app 13-41-17-539.app` 等多次 Finder 重命名副本为证）。排查：部署副本 `codesign -v --deep --strict`、`spctl --assess`、quarantine 均正常——**app 本身没坏，坏在“点击的那一瞬间”**。旧 build.sh 有两处非原子：① `rm -rf build/FrsetNext.app` 后原地编译，构建数秒内该路径是半成品；② 部署用 `ditto "$APP" "$DEPLOY"` **覆盖合并**，复制期间 `/Applications/FrsetNext.app` 是“新旧混合的半成品 bundle”，此时双击 → 签名封印与磁盘内容不一致 → LaunchServices/Gatekeeper 报“已损坏”。取证补强：废纸篓中 `04-37-35` / `04-40-42` / `04-42-17` / `04-43-53` 四份副本 `codesign -v` 报 **`code object is not signed at all`**——正是构建窗口期（二进制已重建、尚未签名）被点开的产物。修复（v31）：编译/签名/校验全部在 `build/.staging/FrsetNext.app` 暂存包内完成 → **rename 换位**（同卷原子）到 `build/FrsetNext.app`；部署同样 `ditto 到 /Applications/.FrsetNext.app.staging.$$` → 重新签名 + 去 quarantine + 严格校验 → rename 换位 → `lsregister -f` 重注册 → 最终路径再校验；任一步失败保留旧版回滚。**效果：对外可见的两个路径任何时刻都是完整可启动包**，构建期间双击只会启动上一版，不再出现“已损坏”。回归实测：app 运行中重新构建+部署，旧进程不受影响、两份产物均 `valid on disk`、`open` 启动成功。日常打开 `/Applications/FrsetNext.app`（`build/` 下仅作构建产物）。排障三件套：`codesign -v --deep --strict`、`spctl --assess -vv`、`lsregister -f`。注意：`pkill -f "FrsetNext"` 会匹配到自己的 shell 命令行（路径含该串）导致自杀退出码 137——统一用 `pkill -x FrsetNext`。

14. **屏幕录制“开关是开的、却一直提示要授权”的最终定性（2026-10-18，v32）**：
   - **现象取证**：`screencapture -l` 抓系统设置窗口确认——`FrsetNext.app` 的开关 **knob 在右 = 开**（用户没记错）。但 app 经 LaunchServices（双击）启动后：`CGPreflightScreenCaptureAccess()=false`，`SCShareableContent` 抛 **`SCStreamError.userDeclined`（-3801，“用户拒绝了 TCC”）**，即系统在运行时确实拒绝。
   - **对照实验**：同一二进制从终端直接启动 → preflight=**已获得**（因为继承了 shell/WorkBuddy 的 responsible-process 授权，是**假阳性**）；从 `open`/LaunchServices 启动 → 未获得。把废纸篓中 `04:17`（ad-hoc）、`12:46`（证书）、`13:41`（证书）三个历史副本分别复制到 `/tmp` 用 `open` 启动 → **全部“未获得”**。
   - **结论**：TCC 记录与**任何现存二进制**的 code identity 都不匹配。开关保持 ON 只代表记录存在，实际 `csreq` 校验失败。macOS 对自签名/重新签名的 app 把屏幕录制授权绑定到具体二进制身份（cdhash）；开发期每次重新构建/重新签名都会让旧记录失效，而设置界面**不会**把开关自动拨回 OFF——于是表现为“我明明给了权限、它却一直要权限”。
   - **为什么证书签名没救回来**：证书签名让 requirement 从 cdhash 变成 `identifier + certificate leaf`（跨构建稳定），但**已经存在的那条旧记录不会因此自动更新**；它仍指向旧二进制。证书只能保证“刷新一次后，后续重建不再失效”，不能让旧记录复活。
   - **处置（用户明确要求不要动设置，故未执行，仅记录）**：对**最终版二进制**刷新一次记录——设置 → 隐私与安全性 → 录屏与系统录音，把 `FrsetNext.app` 开关**关一下再打开**（或 `-` 移除后 `+` 重新添加 `/Applications/FrsetNext.app`），然后重启 app。此后只要 bundle 不再重新签成不同身份，授权保持。
   - **代码侧已做（v32）**：`ScreenshotManager` 新增 `probePermission()`——权限判定不再以 `CGPreflightScreenCaptureAccess()` 为硬闸门，改用 ScreenCaptureKit 的 `SCShareableContent`（真实抓屏能力）作权威判据；`ensureScreenRecordingPermission()` 改为 async，覆盖区域截图/全屏/长截图/取色全部入口。这样 preflight 假阴性时不会再误弹授权窗；但**真实 TCC 拒绝时仍无法绕过**（系统安全边界，任何 API 都拿不到其他 app 的像素）。
   - **长期方案（未实施）**：把抓屏放进一个**永不重新编译的 helper app**（独立 launchd 启动 + XPC 通信），主 app 频繁重建不影响 helper 的 TCC 记录；或取得 Apple Developer ID 后改用 Developer ID + 公证（TCC 对稳定 Team ID 的授权跨版本保留）。

### v44（2026-10-18）GPU 负载恒显示 1% 修复

- **现象**：性能监测 → GPU 页三个环一直显示 `1% / 1% / 0%`，负载历史近乎平线（用户截图）。
- **根因**：**单位重复换算**。C 层 `frset_gpu_usage()` 已把 `Device/Renderer/Tiler Utilization %`
  （0…100）转成 0…1（`v / 100.0`），而 `StatsModulePanels.GPUStatsPanel` 又除了一次 100 ——
  真实 45% 变成 0.0045（显示 0%），**只有 100% 才会显示成 1%**，所以看起来"恒为 1"。
- **修复**：
  1. `GPUStatsPanel` 去掉多余的 `/100`（usage / renderer / tiler 三处）；
  2. `StatsDataProvider` 的 GPU 输出指针先 `initialize(repeating: 0, count: 3)`，
     C 层 `frset_gpu_usage()` 进入时也清零三个输出 —— M 系列偶发缺
     `Tiler Utilization %` 键，不清零会把调用方未初始化内存当读数。
- **口径备忘**：`gpuUsage / gpuRenderer / gpuTiler` 全链路统一 **0…1 比例**，
  `-1` 表示无数据；显示统一走 `MonitorFormat.percent()`。
- **实测**：面板 `45% / 45% / 20%` = `ioreg -r -c IOAccelerator` 的
  Device 45 / Renderer 45 / Tiler 20，逐值一致；负载历史同时有了正常曲线。

## v49（2026-10-18）独立模式卡顿修复 + 风车"公转"修复

**用户反馈**：① 状态栏拆分（独立模式）后十分卡顿、性能开销大；② 风车不是绕中心自转，而是整个图标绕一个点公转。

### 排障（sample 采样实测，6s 窗口）

| 热点 | 占主线程 Timer 时间 | 根因 |
|---|---|---|
| `RotatingLayerView.spin()` 60fps Timer | ~111/336（1/3） | v46 的逐帧 `layer.transform` 写入，每帧触发 `NSViewBackingLayer display` **整视图位图重绘**（sample 栈实证：spin → CA::Transaction::commit → display_if_needed → _NSViewUpdateLayer） |
| `frset_smc_scan` 全量 SMC 扫描 | 单次 ~146ms | 引擎 tick 每 6s 在**主线程**扫 600 个 SMC 键（IOKit mach msg），周期性尖峰卡顿 |

### 修复

1. **风车自转（MenuBarIconStyle.swift RotatingLayerView）**：
   - **公转根因**：macOS `NSView` 托管 layer 的默认 `anchorPoint=(0,0)`（左下角），旋转即绕角点公转。`layout()` 中修正 `anchorPoint=(0.5,0.5)` + `position=视图中心`（同帧、禁隐式动画）。
   - **性能**：回归 `CABasicAnimation`（transform.rotation.z 无限循环，CA 渲染线程插值，主线程零逐帧开销）；v46 要解决的相位跳变改由「变速时读 presentation 当前角度 → remove 旧动画 → 模型层同步该角度 → 新动画 from=当前角」续接——相位连续 + 变速平滑。
2. **SMC 扫描移后台（frset_stats_tick.m）**：每 6s 的 `frset_smc_scan` 放 `QOS_CLASS_UTILITY` 后台线程，结果经 `_Atomic` count release/acquire 发布（数据整块覆盖后原子写计数，主线程无锁读快照不撕裂）。`FSBarCopySensorKeys` 懒扫描同步改原子发布。`g_conn` 启动时主线程打开、之后只读，IOKit 驱动侧串行化，跨线程安全。

### 复测（sample2，6s 窗口）

- 主线程 `RotatingLayerView.spin` = 0、`CA::Transaction::commit` = 0、`frset_smc_scan` = 0（扫描已移后台线程，栈见 MonitorSampler/StatsDataProvider 同款后台模式）。
- 风车连拍验证：图标位置逐帧固定（无位移/画圈），仅叶片角度变化——自转 ✓。
- 遗留观察项：`StatsDataProvider.refresh()` 后台每次刷新也做一次 SMC 扫描（~5% 单核后台占用，不卡 UI），后续可考虑复用引擎 g_snap 快照省掉重复扫描。

## v52（2026-10-18 深夜）状态栏「默认距离太大」排查

**用户反馈**：状态栏（菜单栏）部件之间的默认距离太大。

**实测数据**（`FSBarDumpItems` 增打印自有项屏幕坐标，tick8 稳定后）：

```
CPU/line_chart x=1060 w=66 len=50.1

Network/label  x=1162 w=22 len=6
Disk/mini      x=1184 w=44 len=28

```
规律：**window = length + 16**（每项左右各 8pt 系统内边距），相邻窗口紧贴 → 视觉间距
= 双方 8pt 内边距之和 ≈ 16–25pt（含内容居中余量）。这是 macOS 状态项规则，非我们的 padding

1. ❌ 缩 `item.length` + 部件视图外扩画进内边距：NSButton 会裁掉超出 bounds 的绘制
   （图表右缘被切出白边），不可行，已回退。
2. ✅ 合并成一条（`CombinedModules=YES`）：间距由 `CombinedModules_spacing` 控制
   （none/2/4/6），分隔线可关。实测：4pt 无分隔时整条窄约 25%，2pt+分隔线为注入版原版观感；
   0pt 会因个别部件文本宽度估算偏紧而贴字，不建议。
   合并条内**每个部件仍可单独点击** → `FSBarOpenMonitor(module)` 直达对应模块页（openMerged 按 x 分派），
   与拆分模式的点击语义一致；额外好处是状态项从 5 个减为 1 个（v49 的独立模式开销问题一并缓解）。

**当前处置**：已切至 合并 + 间距 4pt + 无分隔线（候选方案，待用户确认）；
回退方式：部件设置窗勾「合并模块」，或 `widgets.plist` 的 `CombinedModules` 改回 false。

**v52 补充：合并条点击命中偏移修复**

切到合并模式后发现点某个部件会打开相邻模块（实测点 SSD 打开 CPU/RAM）。逐层排查：
- `convertPointFromScreen:` 与 `convertRectToScreen:` 在菜单栏项窗口上都偏（AppKit
  `win.frame` x=1140 / w=168，而截图里部件内容从 1116 起、右缘 1266 —— 整体右移 32pt）；

锚点同样改用鼠标屏幕 x（不再反算窗口坐标）。

## v56（2026-10-19）风车转速跟随 CPU + 中心点 + 状态栏组件逐个验收

**用户反馈**：① 菜单栏风车应像小猫一样「CPU 开销越大转得越快」；② 风车没有中心点；
③ 逐个测试状态栏各个性能组件能否像 STATS 一样单独查看/编辑。

### ① 转速跟 CPU（根因 + 修复）
- **根因**：`SystemCPULoad.current()` 用 `host_processor_info` 的**累计 ticks** 直接相除
  → 得到的是「开机以来的平均负载」，几乎恒定（实测 10%~20%），风车看起来匀速。
- 修复：保存上次 ticks，按**两次采样差值**算区间占用 + EMA 平滑（0.6 旧 + 0.4 新），
  采样间隔 3s → 2s。
- 映射改为与小猫一致的 **7 档离散**（0.8s～4.0s）：
  `<10% 4.0 / <25% 3.2 / <40% 2.6 / <55% 2.0 / <70% 1.5 / <85% 1.1 / ≥85% 0.8`。
  换档时打日志「fan 转速换档：CPU x% → 周期 y s」便于验收。

**实测**（6 个 `yes` 压满 CPU）：
```
空载  CPU 23% → 3.2s ／ 32% → 2.6s
满载  CPU 52% → 2.0s ／ 71% → 1.1s ／ 88% → 0.8s
释放  CPU 64% → 1.5s ／ 47% → 2.0s
```

## v58（2026-10-19）性能：部件点击打开延迟 450ms → ~200ms + 隐藏面板采样门控

**用户反馈**：状态栏拆分后，点部件要等一下面板才弹出来，动效差、性能开销差。

### 测量方法

端到端延迟 = `screencapture` 同源的 CGWindowList 每 5ms 轮询（面板窗口首次 onscreen →
alpha≥1）；配合 `sample <pid>` 抓点击瞬间主线程调用栈。所有数字都是真机 CGEvent 点击实测。

### 根因（三个，都不是引擎点击链路本身）

1. **首次显示 = 全量 SwiftUI 布局**：面板三页（主页/性能/中转）常驻，第一次
   `makeKeyAndOrderFront` 在同一调用里做完整布局 —— sample 显示 ~400ms 全部耗在
   `updateConstraintsIfNeeded → NSHostingView.minSize → ViewGraph layout`。
2. **两套动画没对齐**：窗口 alpha 淡入 0.18s + SwiftUI 弹簧 0.32s，且弹簧在窗口还
   透明（alpha=0）时就开始跑，等窗口可见时动画已过半 —— 观感是"弹一下"。
3. **隐藏面板也在全量重绘**：MonitorSampler 固定 2s 采样 + 三页常驻 → 面板关着时
   性能页仍每 2s 重绘一轮（用户视角"什么都没开却一直在耗"）。

### 修复

| # | 改动 | 文件 |
|---|---|---|
| 1 | **启动空闲预热**：2s 后 alpha=0 离屏 `orderFrontRegardless`，`presentation.visible=true` 真正布局一次（实测 visible=false 时 SwiftUI 跳过不可见子树，预热只有 45ms 等于没热）+ 性能页预排，然后复位/收窗。一次性 200–330ms | PanelController.swift |
| 2 | 弹簧 0.32→0.24s、窗口淡入 0.18→0.14s（收起同步收紧观感） | PanelRootView.swift / PanelController.swift |
| 3 | **采样门控**：性能页（`MonitorCenterPresenter.presented != nil`）或监测设置页可见 → 用户设置的间隔 + 打开瞬间 `refresh()`；否则 ≥5s。菜单栏部件走 C 引擎自有采样，不受影响 | MonitorSampler / MonitorCenterView / MonitorSettingsPane |

**试过但回退**：把 `presented = module` 推迟到 `makeKey` 之后再置 —— 实测更差
（opacity 0 布局一次 + visible 再布局一次，makeKey 176–277ms）。
